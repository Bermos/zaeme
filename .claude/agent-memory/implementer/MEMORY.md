# Implementer memory

What implementers of Bermos/zaeme learn the hard way. One line per lesson, dated,
under the heading it belongs to. Merge duplicates; do not drop.

The entries dated 2026-09-14 are the seed: they are read out of `CLAUDE.md`, the test
suite and the open issues at the moment this file was created, not out of a run.
Everything after them is earned.

## Checks that prove less than they look

- 2026-09-14 (#63 review): A CHECK THAT RECOMPUTES THE SERVER'S OWN ANSWER FROM THE SERVER'S OWN RESPONSE CANNOT FAIL. `ci-upgrade-check` summed the category debits out of `budget.expenses[].lines` and compared them to `totalCents` — which `computeTotalCents` produces by summing exactly those lines — so it restated what it was checking, passed 0 == 0 under the very mutation it looked like it covered, and still counted towards an anti-vacuity floor. The honest form is a figure the CHECK chose: write an expense of 3000 and require the total to move by 3000.
- 2026-09-14 (#63 review): TWO FLOORS THAT DISAGREE FAIL AT THE WRONG END. A producer that accepted "at least 2 expenses" and a consumer that demanded "at least 24 assertions" over a canary worth 20 meant a future cleanup in `api-smoke.sh` would pass the snapshot and then exit 1 with "proved almost nothing" AFTER every check it could run had passed. Count the floor from the code, write the arithmetic into the comment, execute it (a snapshot trimmed to the canary alone), and make the producer refuse anything that would make one of the counted assertions unreachable.

- 2026-09-14 (#63): AN EMPTY DATABASE MAKES EVERY BACKFILL A NO-OP, and that is what CI proved until now. Executed both ways: delete the `UPDATE` that points existing share rows at their member account in `0006_red_redwing.sql` and the chain still applies to an empty Postgres, seeds, boots and passes the whole smoke suite (266 of 266 locally) — against a database the previous release filled it dies on `ALTER COLUMN account_id SET NOT NULL`, "contains null values". A mutation that is green in `api` and red in `upgrade` is the shape to expect from anything a migration does to rows.
- 2026-09-14 (#63): the app HEALS some migration damage on read, which hides it. `ensureEventAccountsWithin` recreates `Uncategorised` and `Rounding` the first time a budget is loaded, so a migration that seeded no chart of accounts for existing events still reads 200 and still balances — the money is simply missing from the trip total. What exposes it is a WRITE naming a category the migration was responsible for creating (`category: 'Food'` → 422 "This event has no category called Food"). Assert on a named write, not only on a read coming back.

- 2026-09-14: A CHECK THAT PASSES WHEN THE THING IS BROKEN IS WORSE THAN NO CHECK. Three shipped in one branch (#57 review): a settings PATCH asserting `"configured":true` rather than the value written (an implementation that discarded its input passed all 168); a budget-currency assertion on a trip whose FIRST expense happened to be in the base (reverting the fix stayed green); and a 422-on-an-unfetchable-currency as the only FX-client coverage (a moved host, a renamed field and a real 404 are all the same 422). Each needed the same remedy: make the check depend on the value, and on a fixture where the wrong answer differs from the right one.
- 2026-09-14: A precondition a smoke check needs must be CREATED by the script, not assumed. The instance base currency can only be changed while no expense disagrees, so the block that proves the change works runs first AND deletes every expense it can reach through `/api/v1` — otherwise it proves the refusal on a re-run and the value on a fresh database, which is the worst of both.
- 2026-09-14: `scripts/api-smoke.sh` RE-RUNS against a database that already has the last run's rows, so a new check must be idempotent: mint your own event, and never assume the instance is in its default state (a check that only passes on a fresh Postgres passes CI and fails the first person who runs it twice).
- 2026-09-14: The exact number to raise `MIN_SMOKE_CHECKS` by is `git diff scripts/api-smoke.sh | grep -cE '^\+\s*(check|contains|equals) '` — the leading-whitespace form matters, because every check inside an `if [ -n "$ZAEME_TEST_*_COOKIE" ]` block is indented and counts towards the floor too.
- 2026-09-14: `pnpm test` is vitest, and **vitest does not typecheck**. A type error in a Vue file or a server handler passes the tests and fails `pnpm typecheck` (`nuxt typecheck`, vue-tsc) — which CI runs as its own step. Run both.
- 2026-09-14: `pnpm smoke:passkey` runs nowhere but a terminal — it drives the real WebAuthn ceremony with a software authenticator (`scripts/webauthn-authenticator.mjs`), and a green pipeline still says nothing about that surface. `pnpm smoke:api` used to be in the same sentence; since #14 the `api` job runs it on every push.
- 2026-09-14: CI runs **no database** (#14), so anything whose behaviour depends on a real query — an ordering, a correlated sub-select, a cascade, a unique constraint — is proved by nothing in the pipeline. Stand up a scratch Postgres and run it. **Superseded 2026-09-14 by the `api` job** (#14): CI now boots `.output/server/index.mjs` against Postgres and runs all 106 `smoke:api` checks, poster round trip and both session halves of the boundary included. `smoke:passkey` still runs nowhere but a terminal.
- 2026-09-14: `pnpm smoke:api` needs no dev server and no `pnpm dev`: the BUILT output boots with `DATABASE_URL`, `PORT`, `BASE_URL`, `BETTER_AUTH_SECRET`, `ZAEME_SERVICE_TOKEN` and `ZAEME_ENTERPRISE_OWNER_ID` and nothing else. Booting the build is the only check that catches a module that resolves at build time and not at boot — `pnpm build` exiting 0 does not.
- 2026-09-14: `scripts/api-smoke.sh` SKIPS rather than fails, and still exits 0. **16** checks need the session cookies (5 guest-session + 7 owner-admin + 4 non-owner) and **12** need `S3_BUCKET`, so the full suite is 106 and a bare run is **78** — "passed 78, failed 0" and "passed 106, failed 0" are the same shade of green. The `api` job therefore greps for `skip` lines and asserts the trailing count against `MIN_SMOKE_CHECKS`; keep that assertion when you touch the job, and raise the floor rather than lowering it.
- 2026-09-14: The events domain (~3,400 LOC) has almost no coverage (#9). A change there is as good as the test you write for it.
- 2026-09-14: `pnpm lint` is `eslint .` through `withNuxt()` and applies **no markdown rules**, and nothing in CI reads a comment either — a prose-only change passes lint, typecheck, vitest and the `api` job without one assertion touching it. The only check on a doc or a comment is somebody re-reading the code each claim describes, one clause at a time, and saying in the PR which file proved which clause (#54).
- 2026-09-14: A COMMENT THAT IS TRUE OF THREE CASES OUT OF FOUR IS A FALSE COMMENT, and nothing in CI reads it. #26's `(splitMode, weight)` pair was documented in four places as existing "so an edit can re-split without re-typing" — true for `percentage`, `weight` and `exact`, and FALSE for `even`, which honours explicit per-person amounts while recording nothing about which participants were pinned. Enumerate the modes/branches against the claim before writing it, and say what is NOT recoverable in the same breath.
- 2026-09-14: An OPEN issue is not an unimplemented issue. The host half of #8 had already landed on `main` (bee78a3) with a comment on the issue describing it, and the issue stayed open for the admin half. `git ls-tree -r origin/main -- <path>` before writing anything an issue says is missing.
- 2026-09-14: `updated_at` moves on its own — the events schema puts `.$onUpdate(() => new Date())` on those columns, so a hand-built `updates` object must NOT set it and does not need to.
- 2026-09-14: `events_expense.currency` was decorative — `loadBudget` returned `expenses[0]?.currency` and `computeBalances` summed cents across currencies (#25). A column existing is not the feature existing; read the function that consumes it before believing a schema comment.

- 2026-09-14: `GET /api/admin/audit` answers `{entries, summary}` and `summariseAudit` IGNORES the query string — `summary.bySurface` always names every surface and `summary.byActor` every kind, so a filter matching NOTHING still returns them beside `entries: []`. A smoke needle like `'"surface":"me"'` or `'"actorKind":"participant"'` is therefore satisfied by the summary and proves nothing (#51 review: two of six new checks were vacuous, and one of them was the check the PR body cited as proving its decision). Needle on `"path"` or `"actorLabel"`, which appear in no summary. The same trap waits wherever a filtered list ships beside unfiltered aggregates.
- 2026-09-14: A vacuous needle also DISARMS `audit_await`: the poll returns on its first read because the summary already matches, so the write-then-read race it exists to close stays wide open for the `contains` after it. A helper that polls for the wrong string is worse than no helper — it looks armed.
- 2026-09-14: MUTATION-TEST EVERY NEW SMOKE CHECK BEFORE CLAIMING IT PROVES ANYTHING. Break the behaviour on purpose (patch the middleware, rebuild, re-run) and confirm the check you are relying on goes red, one mutation per claim in the PR body. #51 shipped a body asserting that labelling the whole surface one way "would have broken this one" — it broke a different one, and the cited check passed with `entries: []`.
- 2026-09-14: TWO mutations, not one, when a feature has a dispatch AND an arithmetic (#26). "Record the mode and ignore it" reddened 21 of 29 new checks; "keep every refusal but split evenly among the non-zero weights" reddened a different 10. Either alone leaves the other half of the feature unproven — the first says nothing about the proportions, the second nothing about the validation.
- 2026-09-14: A MODE'S HAPPY PATH CAN COINCIDE WITH THE DEFAULT'S. `exact` 6000/3000/1000 of 100.00 is what `even` gives for the same input (explicit amounts are honoured there too), so that assertion stayed green under "ignore the mode" — the only check that distinguishes `exact` is that it refuses a participant with NO amount. Mutation testing is what showed which of the two was load-bearing; do not claim a value check proves a mode until it has gone red.
- 2026-09-14: `totalCents` IS VACUOUS FOR ANY SPLIT ASSERTION — it is the expense amount whatever the shares are, so it passes with the split reversed. Assert a BALANCE instead, and choose one the default gets backwards: seven people and 100.00 by `splitEvenlyCents` gives the four leftover cents to the FIRST four, so percentages that give them to the LAST four fail in both directions if the mode is dropped.
- 2026-09-14: PROVE A FEATURE ON THE SURFACE THE PRODUCT USES, NOT THE ONE THAT IS EASIEST TO CURL. #26 shipped 29 smoke checks that ALL posted to `/api/v1` with the service token, while `BudgetCard.vue` posts to `/api/me` (invite page) and `/api/host` (host page) — three separate zod schemas for one write. Narrowing the two human ones to `z.enum(['even','exact'])` with a `weight` regex matching nothing broke every percentage and weight split a PERSON can make, and left vitest at 172 passed, lint and typecheck clean and the smoke floor still met. `grep -c 'api/me\|api/host'` your own new block before claiming a write path is covered.
- 2026-09-14: On a human surface assert **422, not just "not 200"**: a refusal that arrives as 400 came from the zod schema, which never let the mode through, and a refusal that arrives as 422 came from the domain, having understood it. The two are the same red in a `check … 4xx` and opposite findings.
- 2026-09-14: `contains` needles are matched against RAW JSON, so a message that quotes a name (`has no category called "Sherpas"`) arrives with the quotes ESCAPED (`\"Sherpas\"`) and a needle carrying bare quotes never matches. Needle the unquoted prefix.
- 2026-09-14: A `contains` cannot do arithmetic, and a double-entry invariant is arithmetic. `scripts/api-smoke.sh` now has `ledger_imbalance`/`entry_lines`/`account_id`, three one-line `node -e` helpers over the response body — every machine that can build this app has node, and the alternative (a needle per figure) passes on a budget whose entries do not balance. Make such a helper return a SENTINEL (`no-expenses`, `unparseable`, `no-such-entry`) rather than `0` when it finds nothing, or a dead server reads as a clean bill of health.
- 2026-09-14: MUTATION-TESTED #61, three mutations, and the spread is the point: posting every line to `Uncategorised` reddened 13 smoke checks and ZERO vitest tests (the unit tests pass account ids in directly, so they cannot see a resolver that ignores them); dropping the rounding line reddened 17 smoke checks and 2 vitest tests; crediting the payer the converted total instead of what the group owes, with `assertEntryBalances` neutered, reddened 4 smoke checks and 4 vitest tests. A feature whose only coverage is pure functions has a whole class of wrong it cannot see.
- 2026-09-14: a 2880-case property sweep goes VACUOUS WITHOUT FAILING when the code stops calling the function it sweeps. #61 moved conversion out of `apportionCents` and `test/expense-splits.test.ts`'s sweep kept passing over a call the write path no longer made — 184 green, a heading renamed, and no signal at all that the invariant was gone. When a change removes a call, grep the test suite for the callee before believing the suite still covers it.
- 2026-09-14: 425 lines of domain with zero unit tests is a hole even when the smoke suite covers it: neutering `resolveCategoryAccount` left 184/184 green and lint clean while reddening 13 smoke checks that need a built server and a live Postgres. A function taking an array and an object and returning an element does not need either — 20 lines of vitest reddened it in 300ms. NAMING a coverage hole in the PR body is not closing it.
## Moving a route between credentials

- 2026-09-14: MOVING A ROUTE OFF THE INVITE TOKEN SILENTLY DROPS EVERY CHECK `resolveInviteToken` DID — revocation, expiry, the use-count limit AND the `draft`/`cancelled` lifecycle refusal (`server/domain/invite.ts`). #48 moved expense writes onto a session and lost the lifecycle rule: an expense recorded happily against a cancelled trip, and no test noticed. Before moving a handler off a credential, read what the old resolver enforced BESIDES identity, and decide each one explicitly. `assertEventOpenToGuests` in `server/domain/permissions.ts` is now that rule, shared by both paths.
- 2026-09-14: The same move also drops revocation as a control surface for good: standing becomes "an RSVP row exists with my email", and an RSVP row OUTLIVES the link that produced it. Revoking an invite no longer withdraws anything the account can do. That is a consequence to name for the owner, not to paper over.
- 2026-09-14: When two gates answer the same verb (`addExpenseAsPlanner` on `/api/host`, `addExpenseAsParticipant` on `/api/me`), make their role sets AGREE and pin it with a test that reads both. #48 shipped a review round where `logistics` was 403'd on one surface and 200'd on the other. Take the narrower side: widening a role later is additive, un-widening after it ships is not.
- 2026-09-14: Gating a WRITE behind an account forces a decision about the READ that nobody asks for: the screen must tell an unidentified visitor why they cannot write, and the cheap way to do that — one condition for "show the card" — silently starts rendering the DATA to them too. Keep "who may write" and "who may see the figures" as separate props, and make the second one required so the next caller has to decide. A capability that did not move can still change what the page says by default.
- 2026-09-14: A gate that returns "the strongest standing" must not let a weak row short-circuit a stronger one. `assertParticipant` returned `logistics` on the planner row and never looked for the RSVP, so a logistics planner genuinely on the trip was refused by their own planner row.

- 2026-09-14: When a SECOND piece of code answers a question a gate already answers, it must draw the SAME line or the two contradict each other about one request. `findPlannerRoleBySlug` counted any planner row as planner standing, including `logistics` — the one role `assertParticipant` deliberately refuses to count — so the audit called a caller a planner for the very request the handler answered as a participant (or refused outright). Re-read the gate's exclusions, not just its happy path, before writing a cheaper version of it.
- 2026-09-14: A label branch for a case that cannot happen yet is still a decision. `/api/me` with no event in the path has no mutating route today; filing it as `participant` would have been a claim about an event not in the request the moment somebody adds `PATCH /api/me/profile`. It got its own kind (`account`) rather than a comment.

## Boundaries the tests hold, and what they actually assert

- 2026-09-14: since #25 the instance base currency is an INVARIANT, not just a default: every expense freezes `base_currency`/`fx_rate`/`amount_base_cents`, balances are the plain sum of the base cents, and `PATCH /api/admin/settings` answers 409 while any expense disagrees with the requested base. Loosening that refusal silently re-labels history — it is the thing that lets `loadBudget` state one currency over a column of sums.
- 2026-09-14: `suggestSettlements` walks debtors in BALANCE order (the list is sorted by net descending), so the SMALLEST debt is matched first. Any test pinning the plan has to expect that order; it is not "largest first" despite the doc comment's wording.
- 2026-09-14: `test/api-boundary.test.ts` enforces the three credentials and the admin gate's import boundary in both directions. When it fails, the route is in the wrong place or reads the wrong credential — it is not the test being fussy. It checks *where* code lives and what it imports; it cannot check that the gate you called is the right one for the route.
- 2026-09-14: `test/api-contract.test.ts` asserts a bijection between the `/api/v1` route tree and `docs/zaeme-api.openapi.yaml`. A route without a spec entry fails it, and so does a spec entry without a route. The bijection is over paths and methods — it says nothing about field names, optionality or status codes, which is exactly where a break for Enterprise hides.
- 2026-09-14: `apportionCents(parts, total, newTotal)` is not only the FX helper — it is the general largest-remainder distributor, so a percentage or weight split is `apportionCents(weights, sumOfWeights, amountCents)` and needs no second rounding path (#26). A part of 0 provably never collects a leftover cent: leftover = sum(remainders)/total and every remainder is < total, so there are strictly MORE non-zero remainders than there are cents to hand out.
- 2026-09-14: A decimal a user TYPES and a column stores (`numeric(12,4)` for a percentage or weight) must be compared as an INTEGER at that scale — `33.33` is `333300` — or "these add up to 100" is a float comparison and 33.33+33.33+33.34 is not 100. Same discipline as `convertCents`'s BigInt; the refusal message then quotes the real sum (`add up to 99%, not 100%`), which is the difference between a fixable typo and a shrug.
- 2026-09-14: A RULE THE FORM AND THE SERVER BOTH APPLY BELONGS IN `shared/utils/` — Nuxt auto-imports it into app AND server (the precedent is `shared/utils/passkey-context.ts`; the app gets it by auto-import, server code by relative path, a test by direct import). #26 review caught the scale arithmetic living in both `server/domain/expenses.ts` and `BudgetCard.vue`, agreeing exactly and executed on one side only — the drift symptom being a running total reading `100% of 100%` beside a server that refuses the save. Keep the RULE shared and the REFUSAL server-side: return `null` rather than throwing, so the shared half carries no h3 dependency.
- 2026-09-14: `docs/zaeme-api.openapi.yaml` carries the string `updateTimelineItem` in a COMMENT reserving the operationId for whoever decides to give the XO that verb. A test asserting the spec "does not mention" a name fails on the reservation — assert on a declared `operationId: <name>` line instead.
- 2026-09-14: `server/utils/passkey-bootstrap.ts` is imported by `server/utils/auth.ts` and by no route handler; the boundary test asserts that. The two circular cases (an unclaimed instance, a locked-out owner with `ZAEME_OWNER_BOOTSTRAP_TOKEN`) are decided against the database and the environment, never against anything the browser asserts.
- 2026-09-14: the instance owner is the first `zaeme_user` by `created_at` (`server/utils/instance.ts`), so a database with ONE account cannot express the 403 half of the admin gate — every session in it is the owner's. Seed two, with explicitly different `created_at` values: rows inserted in one statement can share a timestamp to the microsecond and make the owner whichever one the planner returns that day.
- 2026-09-14: driving the magic-link sign-in from a script needs an `Origin` header on `POST /api/auth/sign-in/magic-link` — better-auth's CSRF middleware answers `403 MISSING_OR_NULL_ORIGIN` without one, and `fetch` does not send it. The token is `zaeme_verification.identifier` (stored plain) and its `value` carries the email, so match on that rather than on "the newest row".
- 2026-09-14: the mail dry run's `[email:dry-run]` log prints the magic link twice — the `preview` field truncates the token, the `links` array does NOT. Read `zaeme_verification` anyway, and match the row on the email inside `value`: "newest row wins" picks the wrong token exactly when you are signing in two accounts in a row.
- 2026-09-14: The contract test polices paths, methods and operationIds and reads **no comments**. `docs/zaeme-api.openapi.yaml` and the `/api/v1` handlers carry long prose that CI cannot falsify, and two comments had been wrong about timeline editing since `bee78a3` (#10 fixed them). Enterprise vendors that YAML, so a stale comment there misinforms another repository — a comment-only diff is safe, and is owed whenever the surface it describes moves.
- 2026-09-14: `/api/me/**` is the ACCOUNT surface — a session, no planner row required — and since #48 it holds expense writes as well as the `/me` aggregation. The gate is `assertParticipant` in `server/domain/permissions.ts` (planner row, or an RSVP whose `guestEmail` is the account's lowercased email). Guest-surface writes that need an identity belong here, never in `server/api/invites/**`.
- 2026-09-14: `server/middleware/audit.ts` records mutations at the edge; a new route needs no audit code. It must keep returning early for `/api/v1` and `/api/auth` — a change that drops those early returns puts a cookie read next to the machine surface.
- 2026-09-14: Adding a surface to `/api/v1` is a DECISION, not a default (#8). Enterprise generates MCP tools from the spec, so a route added there becomes a verb the model can call. Host and guest surfaces are the normal home for a new feature; `/api/v1` needs the owner's yes.
- 2026-09-14: The contract test's bijection is over paths and methods, so ADDING a field to an existing `/api/v1` response passes every check while still changing what Enterprise's generated client sees. Say in the PR what changed shape, even when CI is green.
- 2026-09-14: Two sequential writes that SWAP a value are a trap: lose the second and the pair is left sharing it, after which every retry computes `a === b`, writes the same value twice, answers 200 twice and changes nothing — a dead control with no error. `sortOrder` reordering had exactly this shape in both timeline editors. Make a swap one statement, and have it renumber unconditionally so it also clears ties somebody else made.
- 2026-09-14: Two adjacent `string` parameters are a regression waiting to happen — transposing `(eventId, itemId)` type-checks, passes every structural test, and 404s the whole route in production. A named parameter object is the only thing in this repo that catches it; a test pinned to the call site cannot.
- 2026-09-14: A surface with no add and no delete has no escape hatch. Before shipping a read-plus-edit screen, ask what the user does when an edit wedges something — on `/admin` the answer cannot be "go to `/host`", because `/host` 403s the non-planning owner that surface exists for.
- 2026-09-14: A test that pins a SQL statement's SHAPE (a `row_number()`, one `update`) proves nothing about what it computes. Deleting a transposition, pinning a delta, and dropping a `where event_id` so a move renumbers every row on the instance all left `pnpm test` green. Since #49 there is a CI job with a migrated Postgres and an owner cookie — put the assertion in `scripts/api-smoke.sh`, execute the operation, and assert the RESULT. Raise `MIN_SMOKE_CHECKS` by exactly the number of checks added.
- 2026-09-14: When code recomputes positions from an ordering, every query the UI draws that list from must break ties on the SAME last key. The timeline renumbered by `…, created_at, id` while three list queries stopped at `created_at`; ids are cuid2, so on a tied list the first click moved a different row than the one the user pointed at. Assert it as one rule over every `orderBy` of the table.
- 2026-09-14: `is distinct from` in an UPDATE is not free: skipping unchanged rows also drops them from the statement's LOCK set, so a concurrent writer's change to them is never rechecked. If the operation claims an invariant over ALL the rows, open it with `select id … where … order by id for update` in a transaction — which also pins lock order and stops two writers deadlocking.

- 2026-09-14: `summariseAudit` groups on the COLUMN (`.groupBy(auditLog.actorKind)`), so a new `actorKind` shows up in the counts for free. The two places that do NOT learn it for free are the zod enum in `server/api/admin/audit/index.get.ts` and `ACTOR_ITEMS` in `app/pages/admin/audit.vue` — miss either and the owner silently cannot filter for that category (#51). `test/api-boundary.test.ts` now reads the enum out of the schema and asserts both agree.
- 2026-09-14: A boundary assertion of the form "X appears after the /api/v1 guard" is an assertion about the FILE, not about the code path: extract X into a helper declared above the handler and it breaks while the behaviour is unchanged. Pin the CALL SITE string (`resolveSessionActorKind(match.surface`), not the symbol.
- 2026-09-14: `/admin/audit`'s filters compose (`actorKind` + `surface` + `eventSlug`), and asking for `actorKind=planner&eventSlug=<slug>` alone also returns the `/api/host` rows for that event. Any assertion about what the ACCOUNT surface recorded must pin `surface=me` too, or it passes on a row from the surface it is not testing.
- 2026-09-14: since #61 the budget is a DOUBLE-ENTRY LEDGER: `events_account` (member/category/rounding per event), `events_expense` is a journal header and `events_expense_share` holds ALL its lines — signed, `account_id` never null, summing to zero in both currencies. `assertEntryBalances` refuses an entry that does not, as a 500, because every caller-fixable input was already refused upstream. The trip total is the sum of DEBITS into category accounts, never an account's net (which is zero by design), so a member-to-member transfer is excluded structurally and #28 needs no `kind` flag.
- 2026-09-14: base cents on a share are STILL apportioned as a group (#25), and #61 kept it after trying not to. Converting each share on its own to give the `Rounding` account something to hold does not surface a rounding artefact — it INVENTS a cent of liability and files it under a name that makes it look discovered: three people severally owe 83.68 for a thing that cost 83.67, the payer is credited 83.68 for handing over 83.67, `paidCents` stops meaning what they paid, and the error is bounded by N/2 cents PER ENTRY and accumulates. An account with nothing to do is the right answer, not a vacuous criterion; keep the mechanism (compute the residual, post a line when it is non-zero) and let #59 be what fills it.
- 2026-09-14: "this criterion would be satisfied vacuously" is not a licence to manufacture the thing it describes. Ask first whether the vacuum is the CORRECT state of the system — if it is, assert the vacuum (no rounding line is written, the account holds 0) and cover the mechanism with a direct unit call.
- 2026-09-14: A lazy seeder that runs on every read cannot be paired with a delete: `ensureEventAccounts` re-created the `Tickets` account the moment anybody looked at the budget after removing it, and only the smoke check that asserted it was GONE noticed. The rule that works: seed the full starting set only when the event has no accounts at all, and afterwards ensure only what the code genuinely depends on (`Uncategorised` and `Rounding`, both `isSystem`).
## Running things locally (smoke scripts, a scratch database)

- 2026-09-14 (#63): `pg_dump -Fc` the database at N-1 ONCE and `pg_restore` it into a fresh database per attempt — a mutation of a migration is then a 2-second loop instead of rebuilding and re-smoking the previous release (~4 minutes) every time. Two full builds plus two smoke runs of a base/head rehearsal cost about four minutes locally; `pnpm build` is ~85s.
- 2026-09-14 (#63): `scripts/api-smoke.sh` DELETES every expense it can reach through `/api/v1` in its base-currency block, which is near the TOP of the file. Anything that inspects rows written before the run has to happen first, or it is asserting against a budget the suite just emptied.

- 2026-09-14: `pkill -f "PORT=<port>"` does NOT kill a node server started by a background tool call — the pattern matches the wrapper shell, not `node .output/server/index.mjs`, whose own argv carries no port. The tell is the next start exiting 0 with `EADDRINUSE` in its log while curl keeps answering from the stale build. Identify the process by `tr '\0' '\n' < /proc/<pid>/environ | grep PORT=` and `kill -9` that pid.

## Deploys, builds and the platform

- 2026-09-14 (#63): BRANCH DELETION IS BLOCKED from this environment — `git push origin --delete` answers "the remote end hung up unexpectedly" and then "Everything up-to-date" (the branch survives), and the REST `DELETE /git/refs/heads/...` answers 403 "Write access to this GitHub API path is not permitted through this proxy". So a scratch branch pushed for evidence is permanent until a person deletes it: push one only when the run is worth it, name it so nobody merges it, and say in the PR that it is still there.
- 2026-09-14 (#63): with `push` + `pull_request` both on and one concurrency group, opening a pull request CANCELS the push run for the same commit (observed: run 34892127007 cancelled mid-`ci` the moment 34892164055 started). That is the dedupe working, not a failure — but the commit then carries a cancelled run beside the green one, so say so before somebody reports it as flaky CI.

- 2026-09-14 (#63): drizzle's migrator decides what to apply from the JOURNAL's timestamps, never from the file's content, and records applied migrations in `drizzle.__drizzle_migrations` (`id`, `hash`, `created_at`). So editing a migration that a deployed instance has already applied changes nothing anywhere — not in CI's `upgrade` job and not in production — and counting that table either side of `migrate()` is the only way to tell "applied yours" from "applied nothing", which is what `scripts/migrate.mjs` now prints.

- 2026-09-14: Merging to `main` ships. Kitchen builds the commit with buildpacks per `kitchen.json` and the `migrate` task runs on the way in; **a failed task stops the deploy**, leaving production on the previous release. The symptom is "my change is not there", not an error page.
- 2026-09-14: `engines.node` in `package.json` is read into `BP_NODE_VERSION` by Kitchen and handed to the node-engine buildpack verbatim. Dropping it as boilerplate silently upgrades Node on the next build.
- 2026-09-14: `kitchen.json` is the only honest answer to "what does a deploy run": `node scripts/migrate.mjs`, plain .mjs because a production install prunes drizzle-kit away. `pnpm db:migrate` (`drizzle-kit migrate`) is LOCAL only and runs under a different dependency set, so reproducing a failed deploy with it can succeed where the deploy failed. `server/database/drizzle.config.ts`'s header claimed the opposite until #54/#55 corrected it.
- 2026-09-14: Grepping for a wrong claim finds mostly RIGHT ones: 5 mentions of `db:migrate` outside the memory, and only the config header was wrong (#54). `README.md:94` uses it legitimately for a from-a-clone self-host, where the dev install has drizzle-kit — so "local development against a scratch database" would have been too narrow a correction to write. Read each hit's surrounding paragraph before calling it stale; a command can be right in one context and wrong in the next.
- 2026-09-14: There is no Dockerfile and no workspace — zäme is a single flat package. A change that assumes `packages/*` or a build stage is thinking of the pre-transplant layout or of Enterprise.
- 2026-09-14: `actions/setup-node` with `node-version-file: package.json` reads `engines.node` — the same field Kitchen turns into `BP_NODE_VERSION`. Use it in any new job rather than hard-coding a major, so CI and the buildpack cannot drift apart silently.
- 2026-09-14: writing a secret to `$GITHUB_ENV` does NOT keep it out of the build log — the runner reprints a step's whole `env` block in the next step's group header. It needs `::add-mask::` on stdout BEFORE the value is first printed, which means a script whose stdout is redirected into `$GITHUB_ENV` can never mask anything: have it append to the `$GITHUB_ENV` file itself and keep stdout for the workflow command. Escape `%` as `%25` in the mask payload first, or a percent-encoded value (every better-auth cookie) masks a string that never appears.

## Types that stop guarding

- 2026-09-14: `db.execute<T>(sql`…`)` returns a pg `QueryResult`, not an array — `[...result]` does not type-check and `result.rows` is the list. `db.select()` returns the array directly. Two shapes in one module.
- 2026-09-14: typing a helper that runs inside a drizzle transaction as `Db | <transaction type>` does not compile; the transaction generic is internal and changes shape between minor versions. `Pick<ReturnType<typeof useDb>, 'select'>` names the one method the helper needs and survives the upgrade.
- 2026-09-14: a drizzle `numeric(p, s)` column comes back from Postgres PADDED TO ITS SCALE — `'1'` written to `numeric(20,10)` reads back `'1.0000000000'` — so every string assertion and every rendered rate needs the trailing zeros trimmed on read. Nothing type-checks this: the column is `string` either way.
- 2026-09-14: A guard typed `(ev: { status: string })` accepts any row with a `status` — an RSVP, an invite — and keeps compiling if a value in `text('status', { enum: [...] })` is renamed out from under it, leaving the comparison matching nothing with `pnpm typecheck` green. Type a schema-value guard `Pick<typeof tables.X.$inferSelect, 'field'>`. Same shape as `events_expense.currency`: a value nothing notices has stopped matching.
- 2026-09-14: reading two tables into a lookup map in the WRONG ORDER is a live concurrency bug, not a style point. `loadBudget` read accounts, then lines; a concurrent write that created a new member account in between left a line whose account was not in the map, and the `?? 'category'` fallback then added somebody's share to the trip total while its owner vanished from the balances. Read the lookup side SECOND so the map is a superset, and prefer a fallback that is obviously wrong on screen to one that is silently plausible.
- 2026-09-14: rows written by ONE insert share `created_at` to the microsecond — Postgres `now()` is transaction time — and cuid2 ids do not sort by age, so `order by created_at, id` over them is stable but ARBITRARY. If the order is part of the contract (the lines of an entry, the shares in the order a person named them) it needs an explicit `seq` column; a comment claiming the written order while the query cannot produce it is two committed comments disagreeing.
- 2026-09-14: a plain `account_id` reference lets a child row point at a parent belonging to a DIFFERENT event. The fix is a composite foreign key `(event_id, account_id) → events_account(event_id, id)` plus the unique index on `(event_id, id)` it needs as a target — Postgres then refuses it instead of the code remembering to.

## Rebase and generated files

- 2026-09-14 (#63): `pnpm db:generate` needs no `DATABASE_URL` (it reads the schema files only) and says "No schema changes, nothing to migrate" on a clean tree. Adding a column to `server/database/schema/*.ts` without regenerating leaves `pnpm lint`, `pnpm typecheck` and all 194 tests green — `git status --porcelain -- server/database/migrations` after a generate is the signal, and it names the file drizzle-kit wanted to write.

- 2026-09-14: a DEFAULT left on a NOT NULL column is a silent-wrong-value generator: an insert that sets some of a group and forgets the rest gets the default for the rest rather than an error. Add-with-default → backfill → `DROP DEFAULT` in the same migration gets both — a statement that survives existing rows, and a column that refuses a forgetful insert afterwards. Keep the TS schema free of `.default()` so the generated snapshot agrees.
- 2026-09-14: `pnpm db:generate` emits `ADD COLUMN <x> integer NOT NULL` with NO default for a `.notNull()` column with no default, which ABORTS on a table that already has rows — and that statement runs as the Kitchen `migrate` task, where a failure strands production on the previous release. Add-with-default → `UPDATE` → `DROP DEFAULT` in the generated file keeps the final shape identical to the snapshot and survives both cases; prove it by replaying 0000..N-1 into a scratch database, inserting a row, and then applying yours.
- 2026-09-14: …and the `UPDATE` is only needed when the backfill value comes from ANOTHER COLUMN (#25's `amount_base_cents = amount_cents`). When the literal default IS the truth for every existing row (#26's `split_mode = 'even'`), add-with-default → `DROP DEFAULT` is the whole migration: `ADD COLUMN … DEFAULT` fills existing rows itself. Replay it against a non-empty table anyway and then confirm a forgetful insert ABORTS — that failing insert is the point of dropping the default, and it is one `psql` line to prove.
- 2026-09-14: Trimming the journal (`meta/_journal.json`, keep `idx < N`) is how you replay only part of the chain into a scratch database to test the newest migration against pre-existing rows. Copy the file first and put it back immediately — it is generated, and a half-trimmed journal committed by accident would skip a migration on every deploy.
- 2026-09-14: a server util that only *calls* `$fetch` inside a function imports cleanly under plain vitest (no Nuxt auto-imports there); one that touches it at module scope does not. Pure helpers can therefore live beside the database code they are used by and still be unit-tested directly.
- 2026-09-14: Editing only a JSDoc comment on a schema column generates NO migration (`pnpm db:generate` says "No schema changes"), and drizzle's `text('x', { enum: [...] })` renders a plain text column — widening that list is a TypeScript change, not a migration. Both are free ways to keep `server/database/schema/*.ts` honest.
- 2026-09-14: better-auth's `useSession()` is safe to call on an SSR'd public page (the invite page does), but `data` is null until the client resolves it. Gate any "you need an account" message on `session.value.isPending`, or a signed-in friend sees the refusal for a frame before it is taken back. NOTE the property is BORROWED: it holds because the session atom defaults to pending and fetches only in the browser. `useSession(useFetch)` returns `isPending: false`, and a version bump could seed the session server-side — so never let PRIVACY rest on it, only timing.
- 2026-09-14: Drizzle migrations are generated (`pnpm db:generate`) and are not mergeable text. After a rebase that brought in another migration, regenerate and re-verify rather than resolving by hand.
- 2026-09-14: `ADD COLUMN x text NOT NULL` with no sensible constant is not the #25/#26 shape (add-with-default → backfill → `DROP DEFAULT`) — there is no constant to default to. Add it NULLABLE, backfill it, then `ALTER COLUMN … SET NOT NULL`: a row the backfill missed then fails loudly instead of inheriting a placeholder.
- 2026-09-14: a migration that writes NEW rows into a table whose old NOT NULL columns it is about to drop has to `ALTER COLUMN … DROP NOT NULL` first — the new rows have nothing to put in `name`/`email`. Order is read the old columns, loosen them, write around them, drop them.
- 2026-09-14: a migration statement that AGGREGATES the table it then inserts into must capture the aggregate in a `CREATE TEMP TABLE … ON COMMIT DROP` first; the second and third inserts would otherwise re-read the rows the first one just wrote. `ON COMMIT DROP` is safe because drizzle's migrator wraps the pending set in one transaction.
- 2026-09-14: drizzle supports PARTIAL unique indexes (`uniqueIndex(...).on(...).where(sql`...`)`), and they are how you keep a uniqueness guarantee when the same key legitimately appears twice per parent: `(expense_id, account_id) where amount_cents >= 0` plus the `< 0` twin gives at most one debit and one credit per account per entry. Predicate on the AS-SPENT amount, not the base one — a tiny expense at a small rate converts to 0 base cents and would collide with itself.
