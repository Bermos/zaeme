# Implementer memory

What implementers of Bermos/zaeme learn the hard way. One line per lesson, dated,
under the heading it belongs to. Merge duplicates; do not drop.

The entries dated 2026-09-14 are the seed: they are read out of `CLAUDE.md`, the test
suite and the open issues at the moment this file was created, not out of a run.
Everything after them is earned.

## Checks that prove less than they look

- 2026-09-16 (#29): A RULE WRITTEN OVER HANDLER SOURCE CANNOT SEE A PAYLOAD THE HANDLER DOES NOT NAME. "Every human handler that answers with a budget signs its receipts" was first written as a grep of each handler for the word `budget` — and passed while `GET /api/invites/{token}` served every receipt UNSIGNED, because that handler is one line (`return getInvitePage(token)`) and the budget is nested three levels inside what it returns. SSR renders the guest page off exactly that route. The honest form computes the producer set FROM THE DOMAIN and closes over it: start at `loadBudget`, add any exported function whose body calls something already in the set, then require every handler calling one to sign. It found 13 where the grep found 12. AND THE CLOSURE ITSELF HAD TWO BLIND SPOTS OF THE SAME SHAPE (#73 review), both executed: the producer regex matched `export function` only, so an `export const f = async () => loadBudget(id)` producer plus an unsigned handler passed all 61 assertions; and the handler filter listed guest+host+account while `adminHandlers` was built three lines above it, so an unsigned admin budget route passed too. A rule computed from a regex has that regex's blind spots, and a filter over "the surfaces I was thinking about" is a list wearing a closure's clothes — enumerate the spellings and the surfaces, and assert the directory you walk is as flat as `readdirSync` assumes.
- 2026-09-16 (#29): AN EXPLICIT `.select({...})` IN THE DOMAIN IS A THIRD PLACE A NEW COLUMN HAS TO BE ADDED, after the schema and the `/api/v1` projection. `listMedia` (`server/domain/events-data.ts`) lists its columns by hand, so `expenseId` reached the OpenAPI document, `v1-shapes.mediaItem` and the type checker while the query never selected it — `null` for every item, lint/typecheck/vitest all green. The only thing that caught it was a smoke check asserting the value the machine surface actually SERVES. Grep `select({` in `server/domain` for the table you touched. Same family as `events_expense.currency`, which `loadBudget` returned from `expenses[0]` while `computeBalances` summed cents across currencies (#25): A COLUMN EXISTING IS NOT THE FEATURE EXISTING — read the function that consumes it before believing a schema comment.
- 2026-09-16 (#29): "NOTHING CHANGED" IS HONESTLY ASSERTED BY COMPARING A RESPONSE TO ITSELF, not to a literal. `money_of <body> <title>` in `scripts/api-smoke.sh` prints every figure and label an entry states about its own money; the pin's rule is `equals "$(money_of "$AFTER" X)" "$(money_of "$BEFORE" X)"`, with no expected value written down at all. A literal there is a constant standing in for "unchanged" and is satisfied by an implementation that rewrites the row to the same defaults. It is also unusable WITH a literal: it joins with `" "` and `[null].join(" ")` is an EMPTY string, so a row with no stated pair expects two consecutive spaces nobody reads correctly twice (#28) — for a by-hand figure, needle the entry's JSON with `contains` instead. AND IT NEEDS BOTH DIRECTIONS: the mutation that made the pin write `fx_rate_source = 'manual'` reddened only the `fetched` fixture, because the `manual` one was already `manual` — a relabel check with one fixture proves one of the two lies it exists to catch.
- 2026-09-16 (#29): A 404 ON A MADE-UP ID DOES NOT PROVE SCOPING. "A photo from another trip cannot be pinned" needs a REAL id from a REAL other event: drop the `eventId` half of the lookup and the made-up id still 404s while a stranger's photograph becomes pinnable. Mint the second event.
- 2026-09-16 (#29): PIN A FORM RULE ON THE ENDPOINT AND THE STATE, NEVER ON A WORD, when the word is overloaded. `receipt` means two things in `BudgetCard.vue` — the paper somebody photographed, and the foreign-currency figure an expense was recorded FROM — and `saveExpense` discusses the second at length. `expect(save).not.toMatch(/receipt/i)` fails on a comment and would pass on a body field called `photo`; `/\/receipt`/` and the ref names do not. Same family as #32's two grep-the-file assertions, which their own doc comments satisfied: a rule a COMMENT can satisfy is not a rule — slice the function, or match the call site.
- 2026-09-16 (#59 review): AN ASSERTION WITH TWO WAYS TO PASS PROVES NEITHER. The block written to catch "was this converted" reading the currency codes instead of the rate used a two-way split, whose recompute leaves a cent on `Rounding` — so `approximate` came back true through its OTHER disjunct and the mutation that restored the broken rule went GREEN on it. One participant makes the residual structurally zero and leaves the rate as the only thing that can answer. Enumerate every disjunct a check can pass through and close all but the one under test.
- 2026-09-16 (#59 review): A ROUND-TRIP FIXTURE PICKED AS A NEAR-INVERSE PROVES REVERSIBILITY OF NOTHING. `1.0865432109` then `0.9203456789` lands every figure back on itself and the comment beside it admitted the exactness was "a property of these numbers" — so the only executed proof of "a manual figure survives" was tuned to succeed, while real non-inverse rates moved a CHF 234.00 hotel to 235.18 and compounded. When a check's success depends on the constants, say which property is being tested and pick constants that do NOT flatter it.
- 2026-09-16 (#59 review): THE `upgrade` JOB CANNOT DISTINGUISH TWO BACKFILL SOURCES THE PREVIOUS RELEASE'S API CANNOT MAKE DIVERGE. "Take the event's currency from its expenses" and "take it from the instance setting" differ only where they already disagree, and #25's 409 made that state unreachable — 0 of 13 events differed in the database that job builds. A mutation verified against a hand-built trimmed-journal fixture is a claim about your terminal; say so in the table rather than crediting CI. What the job CAN see is the other half, so stop skipping the events with no expenses.
- 2026-09-16 (#59): A MONEY FIXTURE HAS TO BE ECONOMICALLY COHERENT, not merely lopsided. The first one had a EUR 245.25 bill costing CHF 208.01, which is a rate no bank charges in that direction (CHF is worth MORE than EUR), and it made the recompute's own rule look wrong: the payer came out owed less than the receipt. Sanity-check the direction of every rate in a fixture against reality before pinning it — the arithmetic will happily prove nonsense.
- 2026-09-16 (#59): adding ONE field to a budget response breaks every `contains` needle that spans it. `'"currency":"CHF","totalCents":44362'` stops matching the moment `approximate` lands between them, in three pre-existing checks. Expect that, and grep the smoke script for adjacent-field needles before believing a new field is additive. They are also matched against RAW JSON, so a message quoting a name (`has no category called "Sherpas"`) arrives with the quotes ESCAPED and a needle carrying bare quotes never matches — needle the unquoted prefix.
- 2026-09-14 (#63 review): A CHECK THAT RECOMPUTES THE SERVER'S OWN ANSWER FROM THE SERVER'S OWN RESPONSE CANNOT FAIL. `ci-upgrade-check` summed the category debits out of `budget.expenses[].lines` and compared them to `totalCents` — which `computeTotalCents` produces by summing exactly those lines — so it restated what it was checking, passed 0 == 0 under the very mutation it looked like it covered, and still counted towards an anti-vacuity floor. The honest form is a figure the CHECK chose: write an expense of 3000 and require the total to move by 3000.
- 2026-09-14 (#63 review): TWO FLOORS THAT DISAGREE FAIL AT THE WRONG END. A producer that accepted "at least 2 expenses" and a consumer that demanded "at least 24 assertions" over a canary worth 20 meant a future cleanup in `api-smoke.sh` would pass the snapshot and then exit 1 with "proved almost nothing" AFTER every check it could run had passed. Count the floor from the code, write the arithmetic into the comment, execute it (a snapshot trimmed to the canary alone), and make the producer refuse anything that would make one of the counted assertions unreachable.
- 2026-09-14 (#63): AN EMPTY DATABASE MAKES EVERY BACKFILL A NO-OP, and that is what CI proved until now. Executed both ways: delete the `UPDATE` that points existing share rows at their member account in `0006_red_redwing.sql` and the chain still applies to an empty Postgres, seeds, boots and passes the whole smoke suite (266 of 266 locally) — against a database the previous release filled it dies on `ALTER COLUMN account_id SET NOT NULL`, "contains null values". A mutation that is green in `api` and red in `upgrade` is the shape to expect from anything a migration does to rows.
- 2026-09-14 (#63): the app HEALS some migration damage on read, which hides it. `ensureEventAccountsWithin` recreates `Uncategorised` and `Rounding` the first time a budget is loaded, so a migration that seeded no chart of accounts for existing events still reads 200 and still balances — the money is simply missing from the trip total. What exposes it is a WRITE naming a category the migration was responsible for creating (`category: 'Food'` → 422 "This event has no category called Food"). Assert on a named write, not only on a read coming back.
- 2026-09-14: A CHECK THAT PASSES WHEN THE THING IS BROKEN IS WORSE THAN NO CHECK. Three shipped in one branch (#57 review): a settings PATCH asserting `"configured":true` rather than the value written (an implementation that discarded its input passed all 168); a budget-currency assertion on a trip whose FIRST expense happened to be in the base (reverting the fix stayed green); and a 422-on-an-unfetchable-currency as the only FX-client coverage (a moved host, a renamed field and a real 404 are all the same 422). Each needed the same remedy: make the check depend on the value, and on a fixture where the wrong answer differs from the right one.
- 2026-09-14: `scripts/api-smoke.sh` RE-RUNS against a database that already has the last run's rows, so a new check must be idempotent: mint your own event, and never assume the instance is in its default state (a check that only passes on a fresh Postgres passes CI and fails the first person who runs it twice). A precondition a check needs must be CREATED by the script too, never assumed — otherwise it proves the refusal on a re-run and the value on a fresh database, which is the worst of both. A cache assertion is the sharpest case: without `$SUFFIX` in the query the second run is served from the first run's cache and the check proves the opposite of what it claims.
- 2026-09-14: `pnpm test` is vitest, and **vitest does not typecheck**. A type error in a Vue file or a server handler passes the tests and fails `pnpm typecheck` (`nuxt typecheck`, vue-tsc) — which CI runs as its own step. Run both.
- 2026-09-14: anything whose behaviour depends on a real query — an ordering, a correlated sub-select, a cascade, a unique constraint — is proved by no vitest test. Since #14 the `api` job boots `.output/server/index.mjs` against Postgres and runs the whole `smoke:api` suite, poster round trip and both session halves of the boundary included, so that is where such an assertion belongs; `smoke:passkey` still runs nowhere but a terminal. `pnpm smoke:passkey` is the exception that stays outside it: it drives the real WebAuthn ceremony with a software authenticator (`scripts/webauthn-authenticator.mjs`) and runs nowhere but a terminal, so a green pipeline still says nothing about that surface.
- 2026-09-14: `pnpm smoke:api` needs no dev server and no `pnpm dev`: the BUILT output boots with `DATABASE_URL`, `PORT`, `BASE_URL`, `BETTER_AUTH_SECRET`, `ZAEME_SERVICE_TOKEN` and `ZAEME_ENTERPRISE_OWNER_ID` and nothing else. Booting the build is the only check that catches a module that resolves at build time and not at boot — `pnpm build` exiting 0 does not.
- 2026-09-14: `pnpm lint` is `eslint .` through `withNuxt()` and applies **no markdown rules**, and nothing in CI reads a comment either — a prose-only change passes lint, typecheck, vitest and the `api` job without one assertion touching it. The only check on a doc or a comment is somebody re-reading the code each claim describes, one clause at a time, and saying in the PR which file proved which clause (#54).
- 2026-09-14: A COMMENT THAT IS TRUE OF THREE CASES OUT OF FOUR IS A FALSE COMMENT, and nothing in CI reads it. #26's `(splitMode, weight)` pair was documented in four places as existing "so an edit can re-split without re-typing" — true for `percentage`, `weight` and `exact`, and FALSE for `even`, which honours explicit per-person amounts while recording nothing about which participants were pinned. Enumerate the modes/branches against the claim before writing it, and say what is NOT recoverable in the same breath.
- 2026-09-14: An OPEN issue is not an unimplemented issue. The host half of #8 had already landed on `main` (bee78a3) with a comment on the issue describing it, and the issue stayed open for the admin half. `git ls-tree -r origin/main -- <path>` before writing anything an issue says is missing.
- 2026-09-14: `updated_at` moves on its own — the events schema puts `.$onUpdate(() => new Date())` on those columns, so a hand-built `updates` object must NOT set it and does not need to. Its precision is MILLISECONDS while the column stores microseconds, so `updated_at` as a lost-update fingerprint cannot tell apart two writes landing in the same millisecond — fine as a second line behind a row lock (#27 takes the event lock first), never a substitute for one.
- 2026-09-14: `GET /api/admin/audit` answers `{entries, summary}` and `summariseAudit` IGNORES the query string — `summary.bySurface` always names every surface and `summary.byActor` every kind, so a filter matching NOTHING still returns them beside `entries: []`. A smoke needle like `'"surface":"me"'` or `'"actorKind":"participant"'` is therefore satisfied by the summary and proves nothing (#51 review: two of six new checks were vacuous, and one of them was the check the PR body cited as proving its decision). Needle on `"path"` or `"actorLabel"`, which appear in no summary. The same trap waits wherever a filtered list ships beside unfiltered aggregates. A vacuous needle also DISARMS `audit_await`: the poll returns on its first read because the summary already matches, so the write-then-read race stays wide open for the `contains` after it.
- 2026-09-14: MUTATION-TEST EVERY NEW SMOKE CHECK BEFORE CLAIMING IT PROVES ANYTHING. Break the behaviour on purpose (patch the middleware, rebuild, re-run) and confirm the check you are relying on goes red, one mutation per claim in the PR body. #51 shipped a body asserting that labelling the whole surface one way "would have broken this one" — it broke a different one, and the cited check passed with `entries: []`. COUNT THE MUTATIONS BY WHAT EACH ONE REACHES — one per claim, because a feature with a dispatch and an arithmetic needs both (#26: "record the mode and ignore it" reddened 21 of 29 checks, "split evenly among the non-zero weights" reddened a different 10) and because the SPREAD is itself the finding (#61: posting every line to `Uncategorised` reddened 13 smoke checks and ZERO vitest tests).
- 2026-09-14: A MODE'S HAPPY PATH CAN COINCIDE WITH THE DEFAULT'S. `exact` 6000/3000/1000 of 100.00 is what `even` gives for the same input (explicit amounts are honoured there too), so that assertion stayed green under "ignore the mode" — the only check that distinguishes `exact` is that it refuses a participant with NO amount. Mutation testing is what showed which of the two was load-bearing; do not claim a value check proves a mode until it has gone red. Same species: `totalCents` is the expense amount whatever the shares are, so it passes with the split reversed — assert a BALANCE the default gets backwards (seven people and 100.00 gives the four leftover cents to the FIRST four).
- 2026-09-14..16: PROVE A FEATURE ON THE SURFACE THE PRODUCT USES, AND WITH THE BODY THE PRODUCT SENDS — two different failures, a release apart. #26 shipped 29 smoke checks that ALL posted to `/api/v1` with the service token while `BudgetCard.vue` posts to `/api/me` and `/api/host`: narrowing those two human schemas broke every percentage and weight split a PERSON could make and left vitest, lint, typecheck and the smoke floor green. #27 then covered all three surfaces — and still missed, because every check sent a body `scripts/api-smoke.sh` had composed while the FORM composed a different one (`splitMode` + `participants` on every correction, the prefilled rate on every correction), so correcting the TITLE of a hand-pinned `even` expense re-split it evenly and moved money between friends, and correcting anything on a foreign row relabelled it as checked against a bank statement. Both survived a full green pipeline. `grep -c 'api/me\|api/host'` your new block, then copy the body the form builds field for field — and know that even then it pins what the SERVER does with that shape, never the form's choice to send it.
- 2026-09-14: On a human surface assert **422, not just "not 200"**: a refusal that arrives as 400 came from the zod schema, which never let the mode through, and a refusal that arrives as 422 came from the domain, having understood it. The two are the same red in a `check … 4xx` and opposite findings.
- 2026-09-14: A `contains` cannot do arithmetic, and a double-entry invariant is arithmetic. `scripts/api-smoke.sh` now has `ledger_imbalance`/`entry_lines`/`account_id`, three one-line `node -e` helpers over the response body — every machine that can build this app has node, and the alternative (a needle per figure) passes on a budget whose entries do not balance. Make such a helper return a SENTINEL (`no-expenses`, `unparseable`, `no-such-entry`) rather than `0` when it finds nothing, or a dead server reads as a clean bill of health.
- 2026-09-14: a 2880-case property sweep goes VACUOUS WITHOUT FAILING when the code stops calling the function it sweeps. #61 moved conversion out of `apportionCents` and `test/expense-splits.test.ts`'s sweep kept passing over a call the write path no longer made — 184 green, a heading renamed, and no signal at all that the invariant was gone. When a change removes a call, grep the test suite for the callee before believing the suite still covers it. And the events domain (~3,400 LOC) still has almost no unit coverage (#9): a change there is as good as the test you write for it.
- 2026-09-15: a DEFAULT that differs BY SURFACE is its own check, twice. `isPlanned` is true when the host says nothing and false when the invite link does; one shared default passes exactly one of that pair, so assert both or the pair proves nothing. The same shape will recur wherever two credentials write one table.
- 2026-09-15: A FAKE CLOCK WHOSE `sleep` ADVANCES A SHARED `t` CANNOT TEST A RATE LIMITER. It serialises concurrent callers, so the broken shape (read the clock, sleep, and only THEN reserve the slot — which lets a whole burst through at once) produces exactly the same numbers as the correct one. Model a sleep as a pending wake-up, release the earliest and move time once; then the wrong implementation lets all three through at t0 and the right one spreads them. Flush microtasks BEFORE the first wake-up or the caller who waited 0 records the clock as it stands after it.
- 2026-09-15: A SMOKE CHECK ON A THIRD-PARTY READ CANNOT BE A `contains` ON WHAT CAME BACK — and it cannot be skipped either, because the `api` job fails on ANY `skip` line. What works is asserting the SHAPE the feature promises in both cases (a `node -e` helper that validates the results when they arrive and the degrade envelope when they do not), plus a derived expectation for anything stateful: `if the first answer was ok then the second must be cached, else it must not be`, which runs and can fail whichever way the afternoon went.
- 2026-09-15: Unicode escapes written into a test file through a tool can arrive as the CHARACTERS they name — `'Zu\u0308rich'` became the composed word, quietly turning an NFC test into a tautology. Bind the two forms to consts and assert they differ before asserting they normalise the same.
- 2026-09-15: TESTING BOTH HALVES OF A GATE IS NOT TESTING THEIR INTERACTION. #32's cooldown was checked only BEFORE the limiter's sleep, so `block()` never reached the two or three callers already asleep — one 429 answered with three more requests over three seconds, which is the exact "retry into a refusal" the module's own comment forbade. The cooldown test used `sleep: async () => {}` and two SEQUENTIAL calls, so nobody was ever mid-sleep when the block fired. Any state a waiter can miss needs re-reading after the wait, and a test where the two events overlap. The same gate also mapped every refusal to one word ("our queue is too long") including the five minutes after a provider said stop, which is the opposite fix: make a gate answer an ENUM and assert the REASON, not just the status.
- 2026-09-16: a REFUSAL check aimed at a fixture an EARLIER check has since changed passes for the wrong reason. #27's "a mixed even split is refused on /api/me" first pointed at an entry a previous check had given an explicit even split — it had stopped being the refusable case at all. Mint the fixture a refusal needs inside the block that needs it.
- 2026-09-16: `ensureMemberAccountsWithin` keys `wanted` on the EMAIL and the LAST name written wins, and both `addExpense` and #27's edit pass `[payer, ...shares]` — so a payer who is also in the split is named by the SPLIT, not by `paidByName`. A smoke check asserting a payer credit by NAME fails on the first fixture where the two differ; assert on the address, which is the identity everywhere in this domain.
- 2026-09-16: AN ASSERTION THAT ENCODES A PROPERTY OF WHICH RELEASE HAPPENS TO BE THE BASE GOES STALE THE MOMENT THE BASE MOVES, and it fails for every branch afterwards regardless of their diffs. `ci-upgrade-check.mjs` asserted `fxRateSource === 'fetched'` for every row the previous release wrote; it passed on #59's own branch only because the release it replaced had no such column, and once #59 was the base the previous release legitimately wrote `manual` rows (the smoke suite writes over a hundred) and the `upgrade` job went red on #27 for somebody else's reasons — its own canary among the casualties. The fix is always the same shape: assert against what the SNAPSHOT recorded, not against a constant, and keep the constant only for the case where the snapshot has nothing to compare (a base predating the column), where it is the right assertion. When you find one, grep the whole file for siblings — and read the label and the figure behind it as ONE fact, because comparing only the label passes a migration that invents a stated amount beside an untouched one.
- 2026-09-16 (#28, and AGAIN in its review): A SMOKE HELPER THAT FINDS AN ENTRY BY TITLE FINDS THE FIRST ONE, and a settlement's title is GENERATED ("Ben → Ana"), so two payments between one pair are two entries with one name. It cost the same block twice: `expense_id` returned the older row, the DELETE removed it, and the checks after it failed for reasons unrelated to what they test — the second time while the sequence-it-carefully fix from the first time was in the file. Sequencing is not the fix; TAKE THE ID FROM THE WRITE THAT MADE IT. Every budget write answers `budget.expenseId` (the domain spreads it into the budget), so `json_field "$RESP" budget.expenseId` is exactly the row just written, whatever it is called. And any read-back assertion about "the refusal wrote nothing" must be a FIGURE (a total, a balance) rather than a by-title lookup, for the same reason.
- 2026-09-16 (#28): UNIT TESTS THAT BUILD THE LEDGER LINES THEMSELVES CANNOT SEE THE WRITE PATH GETTING THEM BACKWARDS. Swapping payer and recipient in `recordSettlement` reddened 15 smoke checks and ZERO of twelve brand-new vitest tests, because those tests pass the pair in themselves — so the only thing that noticed needed a built server, a live Postgres and two cookies. `vi.mock('../server/domain/expenses', importOriginal)` with `addExpense` returning its own arguments pins the TRANSLATION (who is the payer, who is the share, which destination) in 300ms and goes red on exactly that mutation.
- 2026-09-16: A PREFILLED FIELD SENT BACK IS NOT A STATEMENT ANYBODY MADE. The expense form fetches a mid-market rate INTO the rate box as a convenience and submitted it verbatim, so `fx_rate_source` — the column whose whole meaning is "a person checked this against a bank statement", and which a currency recompute trusts — read `manual` on every foreign expense ever recorded through the product. Compare against what the form PUT there (`fxRatePrefilled`) rather than against empty, and send the field only when it differs or the currency moved.

## Moving a route between credentials

- 2026-09-14: MOVING A ROUTE OFF THE INVITE TOKEN SILENTLY DROPS EVERY CHECK `resolveInviteToken` DID — revocation, expiry, the use-count limit AND the `draft`/`cancelled` lifecycle refusal (`server/domain/invite.ts`). #48 moved expense writes onto a session and lost the lifecycle rule: an expense recorded happily against a cancelled trip, and no test noticed. Before moving a handler off a credential, read what the old resolver enforced BESIDES identity, and decide each one explicitly. `assertEventOpenToGuests` in `server/domain/permissions.ts` is now that rule, shared by both paths.
- 2026-09-14: The same move also drops revocation as a control surface for good: standing becomes "an RSVP row exists with my email", and an RSVP row OUTLIVES the link that produced it. Revoking an invite no longer withdraws anything the account can do. That is a consequence to name for the owner, not to paper over.
- 2026-09-14: When two gates answer the same verb (`addExpenseAsPlanner` on `/api/host`, `addExpenseAsParticipant` on `/api/me`), make their role sets AGREE and pin it with a test that reads both. #48 shipped a review round where `logistics` was 403'd on one surface and 200'd on the other. Take the narrower side: widening a role later is additive, un-widening after it ships is not.
- 2026-09-14: Gating a WRITE behind an account forces a decision about the READ that nobody asks for: the screen must tell an unidentified visitor why they cannot write, and the cheap way to do that — one condition for "show the card" — silently starts rendering the DATA to them too. Keep "who may write" and "who may see the figures" as separate props, and make the second one required so the next caller has to decide. A capability that did not move can still change what the page says by default.
- 2026-09-14: A gate that returns "the strongest standing" must not let a weak row short-circuit a stronger one. `assertParticipant` returned `logistics` on the planner row and never looked for the RSVP, so a logistics planner genuinely on the trip was refused by their own planner row.
- 2026-09-14: When a SECOND piece of code answers a question a gate already answers, it must draw the SAME line or the two contradict each other about one request. `findPlannerRoleBySlug` counted any planner row as planner standing, including `logistics` — the one role `assertParticipant` deliberately refuses to count — so the audit called a caller a planner for the very request the handler answered as a participant (or refused outright). Re-read the gate's exclusions, not just its happy path, before writing a cheaper version of it.
- 2026-09-14: A label branch for a case that cannot happen yet is still a decision. `/api/me` with no event in the path has no mutating route today; filing it as `participant` would have been a claim about an event not in the request the moment somebody adds `PATCH /api/me/profile`. It got its own kind (`account`) rather than a comment.

## Boundaries the tests hold, and what they actually assert

- 2026-09-16 (#29 review): A TRANSACTION IS NOT A LOCK, and "read-modify-write in one transaction" is the sentence that hides it. Under Postgres's default READ COMMITTED, `update … where expense_id = X` takes NO lock when it matches no rows — and it matches none in the rival transaction's snapshot precisely when the rival is about to claim the same slot, so two pins to one expense both landed. Lock a row that EXISTS IN BOTH SNAPSHOTS instead (`select … for update` on the parent, inside the transaction); a unique index also works and costs a two-statement dance around a constraint on every replace. Reproduce it with two `pg` clients before believing either the bug or the fix — and note `.returning()` on that update can come back EMPTY under a concurrent delete, so `rows[0]!` is a 500 waiting to happen. Nothing in `pnpm test` can execute an interleaving (no database); pin the MECHANISM structurally, run the interleaving by hand, and say which is which.
- 2026-09-16 (#29): THE GUEST PAGE'S BUDGET COMES OUT OF `GET /api/invites/{token}`, not out of `budget.get.ts` — `getInvitePage` builds it and SSR renders `/i/[token]` off that one resolve. Anything added to a budget has to be handled on BOTH, and that route names no budget in its own source. There are thirteen handlers that answer with a budget on the human surfaces; `removeExpenseAsPlanner` is not one of them (it answers `{removed:true}`).
- 2026-09-16 (#29): `/i/[token]`'s `complete` and `account` are resolved in the BROWSER (a stored identity and `useSession()`), so an SSR fetch of that page renders no expense list at all whatever cookie you send. Verifying a card change over SSR is therefore not possible — check the `__NUXT__` payload for the data instead, and grep `.output/public/_nuxt/*.js` for the new markup to confirm the template compiled. Nothing in this repository drives a browser.
- 2026-09-16 (#59): CURRENCY IS THE EVENT'S NOW (`events_event.currency`), and `events_instance_setting.base_currency` is only what a NEW event is created with — read once, at creation, by all three insert sites. The 409 in `setInstanceBaseCurrency` and `baseCurrencyHold` are gone. The columns on `events_expense` kept the names `base_currency`/`amount_base_cents` deliberately: Enterprise generates a client from them, and renaming them would break another repo to say what the `currency` beside them already says.
- 2026-09-16 (#59): THE RECOMPUTE IS THE ONE PLACE THAT DOES NOT APPORTION. ## Types that stop guarding

- 2026-09-16 (#59 review): `currency !== baseCurrency` IS THE WRONG QUESTION for "was this converted", and it reads like the definition. A payer's stated out-of-pocket figure survives a change of the trip's currency, so a EUR receipt on a trip that moved to EUR has both codes equal and the two amounts nine francs apart — the card printed the receipt, hid the settled figure and hid the rate line that would have explained it, and the budget called itself exact. The rate is the only field that survives every path: `shared/utils/conversion.ts`, one rule, read by the server and the card.
- 2026-09-16 (#59 review): A DERIVED COLUMN THAT OVERWRITES ITS OWN INPUT DESTROYS SOMETHING UNRECONSTRUCTABLE. The recompute rewrote `amount_base_cents` on a row whose payer had typed that figure off a bank statement and kept no copy, while `fx_rate_source` went on saying `manual`. Keep the stated input beside the derived one (`stated_amount_cents`/`stated_currency`) in the SAME migration — a column you wish you had kept cannot be added retrospectively once real money is in the table, and preserving it leaves the behavioural question open for the owner instead of guessing.
- 2026-09-14: `db.execute<T>(sql`…`)` returns a pg `QueryResult`, not an array — `[...result]` does not type-check and `result.rows` is the list. `db.select()` returns the array directly. Two shapes in one module.
- 2026-09-14: typing a helper that runs inside a drizzle transaction as `Db | <transaction type>` does not compile; the transaction generic is internal and changes shape between minor versions. `Pick<ReturnType<typeof useDb>, 'select'>` names the one method the helper needs and survives the upgrade.
- 2026-09-14: a drizzle `numeric(p, s)` column comes back from Postgres PADDED TO ITS SCALE — `'1'` written to `numeric(20,10)` reads back `'1.0000000000'` — so every string assertion and every rendered rate needs the trailing zeros trimmed on read. Nothing type-checks this: the column is `string` either way.
- 2026-09-14: A guard typed `(ev: { status: string })` accepts any row with a `status` — an RSVP, an invite — and keeps compiling if a value in `text('status', { enum: [...] })` is renamed out from under it, leaving the comparison matching nothing with `pnpm typecheck` green. Type a schema-value guard `Pick<typeof tables.X.$inferSelect, 'field'>`. Same shape as `events_expense.currency`: a value nothing notices has stopped matching.
- 2026-09-14: reading two tables into a lookup map in the WRONG ORDER is a live concurrency bug, not a style point. `loadBudget` read accounts, then lines; a concurrent write that created a new member account in between left a line whose account was not in the map, and the `?? 'category'` fallback then added somebody's share to the trip total while its owner vanished from the balances. Read the lookup side SECOND so the map is a superset, and prefer a fallback that is obviously wrong on screen to one that is silently plausible.
- 2026-09-14: rows written by ONE insert share `created_at` to the microsecond — Postgres `now()` is transaction time — and cuid2 ids do not sort by age, so `order by created_at, id` over them is stable but ARBITRARY. If the order is part of the contract (the lines of an entry, the shares in the order a person named them) it needs an explicit `seq` column; a comment claiming the written order while the query cannot produce it is two committed comments disagreeing.
- 2026-09-14: a plain `account_id` reference lets a child row point at a parent belonging to a DIFFERENT event. The fix is a composite foreign key `(event_id, account_id) → events_account(event_id, id)` plus the unique index on `(event_id, id)` it needs as a target — Postgres then refuses it instead of the code remembering to.
- 2026-09-15: `numeric(p, s)` read back through `Number()` is how a coordinate becomes usable arithmetic — the column stays exact decimal (what was typed is what is stored, and it sorts and indexes for a bounding box) while the API view is a JS number, because every consumer of a coordinate does arithmetic and a driver string is a `+` away from concatenation. Money is the opposite case and stays integer cents.
- 2026-09-15: `Number(n.toFixed(6))` decides an EXACT half (…5 in the seventh decimal) from the binary representation, so `8.5416575` rounds DOWN. Do not pin a half-case in a test; pick a fixture that is not on the boundary and say in the comment why.
- 2026-09-15: a shape check that caps decimals must allow the CALLER's precision, not the column's: `String(47.37688659999999)` is what a browser hands over after its own arithmetic and Nominatim answers seven decimals, so a 12-decimal cap refused a legitimate value. Round to the column's scale in the code; cap only what is absurd.
- 2026-09-15: `$fetch(url, options)` with a plain `string` url makes Nuxt's typed-route inference recurse until the compiler gives up — `TS2321: Excessive stack depth`, six copies of it, only under `nuxt typecheck`. eslint and vitest are both silent. A template literal resolves (that is why `server/utils/fx.ts` compiles); a variable does not. Declare the narrow call shape you actually use and cast `$fetch` to it once.
- 2026-09-15: A FIELD NO SCREEN AND NO LOG READS IS A COMMENT PRETENDING TO BE AN ENUM. #32's three `unavailable` reasons reached neither: the card branches on `status` alone, correctly (there is nothing a planner can do about any of them), so the distinction existed only in the type. One `console.warn` on the failure path is what makes it real — it is the only place "OpenStreetMap is busy" and "this instance is blocked" differ, and the second needs a person. Its twin: a WRITE-ONLY field in a form is a rule with no way out — the card set `osmType`/`osmId` on create and offered nothing to clear them, so a place pinned to the wrong feature could never be re-pinned.
- 2026-09-16: a Vue `watch` that RESETS state on change will eat a prefill written in the same tick — `splitMode` clearing `splitValues`, `spentCurrency` re-fetching a rate over the frozen one. A one-shot suppression flag the watcher consumes is deterministic where relying on `nextTick` ordering is not.

## Style and shape

- 2026-09-16 (#29 review): "THIS WIDENS NO READ SET" IS AN ARGUMENT ABOUT THE SERVER AND NOT AN ANSWER ABOUT THE SCREEN. Pinning a receipt let nobody see a byte they could not already fetch from the gallery — correct, reviewed, and still wrong on the surface, because the control was a glyph and the word "gallery" appeared exactly once in the flow: in the toast you get when you take a receipt OFF. Somebody photographing a hotel folio is thinking "evidence for my friends", not "publication". Say where the thing goes BESIDE THE CONTROL, before the decision, not in the confirmation after it — the #67 shape, where a field labelled "Note (optional)" said nothing about who could read it. Withholding the data instead would have been theatre; the fix is a sentence.
- 2026-09-14: Stock Nuxt UI with its default look. The Enterprise design system, the `ui-components` and `navigation` skills, and every instrument-panel idiom are for the other repo and are a review finding here.
- 2026-09-14: `AGENT.md` is the style contract for server code: `#server/...` aliases over deep relative imports, `e.method` over `getMethod(e)`, return the query directly, modern Zod (`z.email`, `z.url`, `z.iso.datetime`).
- 2026-09-14: Domain logic goes in `server/domain/`; handlers stay thin. Cross-event admin reads go in `server/domain/admin.ts` — read the N+1 note at the top of that file before adding one.
- 2026-09-14: Ask `server/utils/mail-status.ts` whether this instance can send mail. Reading `RESEND_API_KEY` directly misses the mail relay in front of Proton Bridge (`KITCHEN_SERVICE_MAIL`) and the dry run.
- 2026-09-14: order two refusals by what the person can ACT on. `removeAccount` checked "holds lines" (409, delete your expenses) before "is a system account" (422, never), so the first answer sent somebody to empty `Uncategorised` and the second refused them anyway. The unconditional refusal goes first.
- 2026-09-15: DRIZZLE-KIT EMITS EVERY CONSTRAINT BEFORE EVERY INDEX, so a composite foreign key whose target is a `uniqueIndex` created in the SAME migration aborts with `42830 there is no unique constraint matching given keys` — on an empty database as well as a full one, which as the Kitchen `migrate` task is a deploy stranded on the previous release. Move the `CREATE UNIQUE INDEX` ahead of the `ADD CONSTRAINT`s by hand (0007 does, with the reason in its header): same statements, same final shape, so the snapshot still matches and the CI drift check stays green. `pnpm build` and `pnpm test` say nothing about this — only running `node scripts/migrate.mjs` does. The inverse, so the rule is not applied where it does not belong (#29): a foreign key whose REFERENCED column is a PRIMARY KEY has an implicit unique index already, so the generated `ADD COLUMN` → `ADD CONSTRAINT` → `CREATE INDEX` order is safe as written. It bites COMPOSITE keys pointing at a unique index the same migration creates. Two lines to check by hand; guessing costs a stranded deploy.
- 2026-09-15: `on delete set null` and a COMPOSITE foreign key are incompatible here: SET NULL nulls every column of the key, including the `event_id` that is NOT NULL, and drizzle-kit does not emit Postgres 15's `SET NULL (column_list)`. So a child that must be event-scoped AND survive its parent's deletion gets `restrict` plus an explicit transaction in the domain (`deletePlaceAsPlanner`), and a single-column reference keeps `set null` (`events_timeline_item.place_id`, where the scoping check is then code and not the database).
- 2026-09-15: replaying part of the chain to test a migration against pre-existing rows takes about a minute and is worth it every time: trim `meta/_journal.json` to `idx < N`, migrate, `insert` a row with psql, put the journal back, migrate again, and read the row. It proved 0007's `ADD COLUMN place_id text` keeps an existing item's `location` and leaves the new column NULL, and that the retry applies 0 — the two things the `upgrade` job asserts.

- 2026-09-14: There are **no `ENABLE_*` feature flags** and no `ADMIN_EMAIL` in the source. - 2026-09-15: EDITING `scripts/api-smoke.sh` BY `s.index(anchor)` IS A TRAP — check names repeat across blocks ("a direction that is not up or down" exists in the timeline block AND in a new one), so a splice whose `end` anchor matches an EARLIER block silently duplicates everything between them. ## Rebase and generated files

- 2026-09-16 (#59): `pnpm db:generate` emitted `ADD COLUMN currency text NOT NULL` for a column whose truth differs per row. The shape that survives a full database AND keeps the snapshot identical is add-nullable -> UPDATE (from the rows that already know the answer) -> UPDATE (the rest, from the default) -> `SET NOT NULL`, hand-written over the generated file; `pnpm db:generate` then says "No schema changes". Proved by trimming `meta/_journal.json` to `idx < N`, inserting an event whose expenses disagree with the instance setting, restoring the journal and migrating: the right backfill answers EUR, the naive one answers CHF, and nothing but the `upgrade` job can tell them apart.
- 2026-09-14 (#63): `pnpm db:generate` needs no `DATABASE_URL` (it reads the schema files only) and says "No schema changes, nothing to migrate" on a clean tree. Adding a column to `server/database/schema/*.ts` without regenerating leaves `pnpm lint`, `pnpm typecheck` and all 194 tests green — `git status --porcelain -- server/database/migrations` after a generate is the signal, and it names the file drizzle-kit wanted to write.
- 2026-09-14: a DEFAULT left on a NOT NULL column is a silent-wrong-value generator: an insert that sets some of a group and forgets the rest gets the default for the rest rather than an error. Add-with-default → backfill → `DROP DEFAULT` in the same migration gets both — a statement that survives existing rows, and a column that refuses a forgetful insert afterwards. Keep the TS schema free of `.default()` so the generated snapshot agrees.
- 2026-09-14: `pnpm db:generate` emits `ADD COLUMN <x> integer NOT NULL` with NO default for a `.notNull()` column with no default, which ABORTS on a table that already has rows — and that statement runs as the Kitchen `migrate` task, where a failure strands production on the previous release. Add-with-default → `UPDATE` → `DROP DEFAULT` in the generated file keeps the final shape identical to the snapshot and survives both cases; prove it by replaying 0000..N-1 into a scratch database, inserting a row, and then applying yours. The `UPDATE` is only needed when the backfill comes from ANOTHER COLUMN; when the literal default is the truth for every existing row, add-with-default → `DROP DEFAULT` is the whole migration.
- 2026-09-14: Trimming the journal (`meta/_journal.json`, keep `idx < N`) is how you replay only part of the chain into a scratch database to test the newest migration against pre-existing rows. Copy the file first and put it back immediately — it is generated, and a half-trimmed journal committed by accident would skip a migration on every deploy.
- 2026-09-14: a server util that only *calls* `$fetch` inside a function imports cleanly under plain vitest (no Nuxt auto-imports there); one that touches it at module scope does not. Pure helpers can therefore live beside the database code they are used by and still be unit-tested directly.
- 2026-09-14: Editing only a JSDoc comment on a schema column generates NO migration (`pnpm db:generate` says "No schema changes"), and drizzle's `text('x', { enum: [...] })` renders a plain text column — widening that list is a TypeScript change, not a migration. Both are free ways to keep `server/database/schema/*.ts` honest.
- 2026-09-14: better-auth's `useSession()` is safe to call on an SSR'd public page (the invite page does), but `data` is null until the client resolves it. Gate any "you need an account" message on `session.value.isPending`, or a signed-in friend sees the refusal for a frame before it is taken back. NOTE the property is BORROWED: it holds because the session atom defaults to pending and fetches only in the browser. `useSession(useFetch)` returns `isPending: false`, and a version bump could seed the session server-side — so never let PRIVACY rest on it, only timing.
- 2026-09-14: Drizzle migrations are generated (`pnpm db:generate`) and are not mergeable text. After a rebase that brought in another migration, regenerate and re-verify rather than resolving by hand.
- 2026-09-14: `ADD COLUMN x text NOT NULL` with no sensible constant is not the #25/#26 shape (add-with-default → backfill → `DROP DEFAULT`) — there is no constant to default to. Add it NULLABLE, backfill it, then `ALTER COLUMN … SET NOT NULL`: a row the backfill missed then fails loudly instead of inheriting a placeholder.
- 2026-09-14: a migration that writes NEW rows into a table whose old NOT NULL columns it is about to drop has to `ALTER COLUMN … DROP NOT NULL` first — the new rows have nothing to put in `name`/`email`. Order is read the old columns, loosen them, write around them, drop them.
- 2026-09-14: a migration statement that AGGREGATES the table it then inserts into must capture the aggregate in a `CREATE TEMP TABLE … ON COMMIT DROP` first; the second and third inserts would otherwise re-read the rows the first one just wrote. `ON COMMIT DROP` is safe because drizzle's migrator wraps the pending set in one transaction.
- 2026-09-14: drizzle supports PARTIAL unique indexes (`uniqueIndex(...).on(...).where(sql`...`)`), and they are how you keep a uniqueness guarantee when the same key legitimately appears twice per parent: `(expense_id, account_id) where amount_cents >= 0` plus the `< 0` twin gives at most one debit and one credit per account per entry. Predicate on the AS-SPENT amount, not the base one — a tiny expense at a small rate converts to 0 base cents and would collide with itself.
- 2026-09-15: POSTGRES COUNTS TWO NULLS AS DISTINCT BY DEFAULT, so a unique index over nullable columns already permits any number of all-null rows and a `where … is not null` predicate changes NOTHING today. It is worth adding (it says which rows the rule is about, keeps the index small, and survives a rebuild with `NULLS NOT DISTINCT`) but a comment claiming a non-partial index "would refuse every hand-typed place after the first" is false — and I wrote it in three files before checking it against a real Postgres.
- 2026-09-15: drizzle-kit emits `ALTER TABLE … ADD CONSTRAINT … CHECK` and `CREATE UNIQUE INDEX … WHERE …` for an EXISTING table without an interactive prompt, and puts the index before the constraint. With no foreign key in the migration there is nothing to reorder by hand — the 42830 trap is specifically a composite FK reaching for an index the same file creates later.
- 2026-09-15: the cheapest proof that a new constraint is safe on a full database is the journal trim: keep `idx < N`, migrate a scratch database, INSERT the rows the constraint is about, restore the journal, migrate again, and then try the inserts it must refuse. For #32 that was three `psql` lines and it is the only evidence the `upgrade` job's answer was going to be green.
