# Architecture

This document describes the technical architecture of zäme. It is intended as a living reference for contributors and self-hosters who want to understand how the pieces fit together.

-----

## Overview

zäme is a single-tenant, full-stack Nuxt 4 application. “Single-tenant” means one instance serves one person (the admin) and their friends. There is no concept of organisations, workspaces, or cross-user isolation beyond the event permission model.

```
Browser
  │
  ├── SSR pages (Nuxt, server-rendered for invite pages / OG previews)
  ├── SPA navigation (client-side after initial load)
  │
  └── Nuxt Server
        ├── /api/**          REST API (H3 event handlers)
        ├── /calendar/*.ics  iCal feed routes
        ├── /mcp             MCP server endpoint
        │
        ├── Better Auth      Authentication
        ├── Drizzle ORM      Database access
        ├── Inngest client   Background job dispatch
        └── Anthropic SDK    LLM calls
```

-----

## Data Layer

### Database

PostgreSQL via [Neon](https://neon.tech). Drizzle ORM for schema definition, migrations, and queries. `neon-http` as the driver.

Schema lives in `packages/db/schema/`. Each domain has its own file:

```
server/
  database/
    schema/
      users.ts
      events.ts
      planners.ts
      attendees.ts
      travel.ts
      todos.ts
      media.ts
      chat.ts
      datepoll.ts
      ical.ts
      timeline.ts       timeline_item (itinerary)
      index.ts          re-exports all tables + relations
    drizzle.config.ts   drizzle config
    migrations/         generated by drizzle-kit
  utils/
    db.ts               db singleton
```

Migrations can be run manually by executing `pnpm db:migrate`.

### IDs

All primary keys use [cuid2](https://github.com/paralleldrive/cuid2) — URL-safe, sortable, no UUID visual noise. Generated in application code before insert, never by the database.

### Relations at a glance

```
User
  ├── EventPlanner (role: owner | co_planner | logistics)
  └── Attendee (userId nullable — guests have no account)

Event
  ├── EventPlanner[]
  ├── Attendee[]
  │     └── TravelGroupCommitment
  ├── TravelGroup[]
  ├── OrganizerTodo[]
  ├── PackListTemplateItem[]
  ├── Media[]
  │     └── TimelineItem (optional pin via timelineItemId)
  ├── TimelineItem[]
  ├── ChatMessage[]
  └── DatePoll
        ├── DatePollSlot[]
        └── DatePollResponse[]

Attendee
  ├── AttendeePackItem[] (personal, seeded from template)
  └── IcalToken
```

## Authentication

[Better Auth](https://better-auth.com) handles all authentication concerns.

### Strategies

| Strategy         | Who                          | Notes                                                     |
|------------------|------------------------------|-----------------------------------------------------------|
| Email + password | Admin + registered users     | Standard credential flow                                  |
| Magic link       | Guests + users who prefer it | Optional, enabled via `ENABLE_MAGIC_LINK` env var         |
| RSVP token       | Guests                       | Single-use token in invite URL — no auth required to RSVP |

### Roles

| Role    | Description                                                                    |
|---------|--------------------------------------------------------------------------------|
| `admin` | Instance owner. Full access to everything. Set via `ADMIN_EMAIL` on first run. |
| `user`  | Invited friend. Can be added as co-planner on specific events.                 |
| Guest   | No account. Identified by email + RSVP token. Can RSVP, chat, upload media.    |

### First-run

On first server start with an empty database, zäme checks for the existence of the admin user. If absent, it redirects all traffic to `/setup` where the admin account is created. `ADMIN_EMAIL` is locked in at this point.

## Event Lifecycle

```
draft ──→ polling ──→ published ──→ completed
  │                                    │
  └──────────────────────────────→ cancelled
```

| Status      | Description                                    |
|-------------|------------------------------------------------|
| `draft`     | Visible to planners only. Brainstorm mode.     |
| `polling`   | Date poll is open. Invite link not yet active. |
| `published` | Invite link active. RSVPs open.                |
| `completed` | Event is past. Read-only, media/memories mode. |
| `cancelled` | Soft-cancelled. Attendees notified via email.  |

Status transitions are explicit server actions, not automatic. Moving from `polling → published` auto-sets `startsAt` from the decided poll slot and sends invites.

## Event Types

| Type      | Differences                                                                           |
|-----------|---------------------------------------------------------------------------------------|
| `hosted`  | Full feature set. You are organising.                                                 |
| `concert` | `ticketUrl` shown, RSVP mode is `cheering`. Publicly visible by default.              |
| `series`  | Parent container. Has child events (`parentId`). Shared chat + media across episodes. |

## File Storage

Cloudflare R2 (S3-compatible). All uploads go directly from the browser to R2 via presigned URLs — the Nuxt server never proxies file bytes.

```
Browser → POST /api/media/presign → Nuxt server generates presigned URL
        → PUT {presignedUrl} (direct to R2)
        → POST /api/media/confirm → Nuxt server records the media row
```

R2 key structure:

```
{eventId}/{mediaType}/{cuid}.{ext}
```

For self-hosters without R2: any S3-compatible storage works (MinIO, Garage, etc.) by setting the same env vars with a custom endpoint.

## Timeline / Itinerary

Each event can have a structured itinerary built from ordered `TimelineItem` rows.

Schema: `server/database/schema/timeline.ts` — `timeline_item` table.

| Column      | Description                                                              |
|-------------|--------------------------------------------------------------------------|
| `type`      | `transport` \| `activity` \| `accommodation` \| `meal` \| `other`       |
| `sortOrder` | Integer; items are displayed ascending by `sortOrder`, then `startsAt`.  |
| `icon`      | Optional Heroicons/Lucide slug override — falls back to type default.    |
| `pollId`    | Forward-reference to a future `DatePoll` row. When set the item is shown as "pending poll decision" in the UI until the poll is decided. |

API: `server/api/events/[slug]/timeline/` — full CRUD, planner-scoped write access.

UI: `app/components/EventTimeline.vue` — drag-reorder, inline editing, type icons.

**Media pinning**: any `media` row can be associated with a timeline item via `timelineItemId` FK. Pinned media appears in-line under its itinerary step.

## Background Jobs

[Inngest](https://inngest.com) handles all async work. Jobs are defined in `app/server/inngest/`.

| Job                | Trigger                             | Does                                               |
|--------------------|-------------------------------------|----------------------------------------------------|
| `rsvp.confirmed`   | Attendee RSVPs yes/maybe            | Send confirmation email with `.ics` attachment     |
| `event.published`  | Event status → published            | Send invite emails to all attendees                |
| `event.reminder`   | Scheduled, 48h before event         | Send reminder emails                               |
| `event.cancelled`  | Event status → cancelled            | Notify all attendees                               |
| `travel.recluster` | New RSVP with location              | Re-run travel group clustering, update suggestions |
| `sbb.refresh`      | Scheduled, daily per upcoming event | Refresh cached SBB connections                     |
| `datepoll.closed`  | Poll deadline passes                | Auto-close poll, notify planners                   |
| `packList.seed`    | Attendee RSVPs yes                  | Copy template items to attendee’s pack list        |

## Fahrgemeinschaft (Travel Groups)

Travel group detection runs as an Inngest job whenever a new RSVP arrives with a location set.

### Algorithm

1. For each attendee with `originStation` set, fetch the optimal SBB connection to `event.venueStation` arriving before `event.startsAt`.
2. Cluster attendees by shared departure station (`originStation`).
3. Within each cluster, find connections that share a leg (same `trainNumber` + `departureTime`).
4. Create or update `TravelGroup` rows. Attendees in the same group are notified via chat message.

### SBB Client (`packages/sbb/`)

Thin wrapper around [transport.opendata.ch](https://transport.opendata.ch/docs.html).

```typescript
// packages/sbb/index.ts
sbb.connections(from, to, { arrival: event.startsAt })
sbb.stationboard(station)
sbb.locations(query)  // autocomplete for origin input
```

For self-hosters outside Switzerland: set `ENABLE_SBB=false`. Travel coordination falls back to a simple “people near you” cluster display with a Google Maps directions link.

## iCal / Calendar

Two endpoints, both unauthenticated (secured by unguessable token):

| Endpoint                          | Content                                                  |
|-----------------------------------|----------------------------------------------------------|
| `GET /calendar/[token].ics`       | All events the token owner has RSVP’d to                 |
| `GET /events/[slug]/calendar.ics` | Single event (public, no token needed for public events) |

Generated by `packages/ics/` using the [ics](https://www.npmjs.com/package/ics) library. Attached to RSVP confirmation emails via Resend.

## Machine API — Enterprise's reach into zäme (ADR-0036)

zäme owns the social domain outright. The Enterprise life-OS keeps no `events_*`
schema and no domain logic; it reaches zäme **only** over a versioned HTTP
contract, and its XO agent's whole events tool surface is GENERATED from that
contract at build time.

**The contract is [`docs/zaeme-api.openapi.yaml`](docs/zaeme-api.openapi.yaml),
and this repository's copy is the source of truth.** zäme serves it verbatim at
`GET /api/openapi.yaml`. The copy committed in `Bermos/Enterprise` is an
explicitly-labelled vendored snapshot, kept so their build can generate offline;
it is downstream of this one.

### Shape

- 30 paths, 40 operations, all under `/api/v1`.
- 33 carry `x-mcp-expose` (the default) and become MCP tools under exactly the
  names the XO already uses — `listEvents`, `scheduleSeriesShowing`,
  `createPartyPlan`, … An `operationId` is a tool name, so renaming one changes
  the model's vocabulary. `test/api-contract.test.ts` freezes the set.
- 7 are plumbing and are deliberately NOT tools: `getEventsSnapshot`,
  `getEventsAttention`, `publishConcert`, `unpublishConcert`, `uploadPoster`,
  `headPoster`, `getHealth`.
- Route handlers are thin. Every operation validates with zod, calls ONE
  `server/domain/` function and projects the result through
  `server/utils/v1-shapes.ts`, so a new column never silently joins a generated
  tool's output.

### Three that carry weight

| Operation | Why it is special |
|---|---|
| `getEventsSnapshot` | Fetched on EVERY XO turn before any tool call. One SQL statement (a `mine` CTE with scalar sub-selects), strong `ETag` + `private, max-age=60, stale-while-revalidate=600` so the steady state is a 304, and it degrades to a valid snapshot with `degraded: true` rather than 5xx. |
| `getEventsAttention` | The facts half of the daily check-in. Stateless and side-effect free; Enterprise keeps the unread guard, the once-a-day throttle and the escalation. |
| `uploadPoster` / `headPoster` | Poster art is content-addressed by SHA-256. The digest is verified **server-side** — the path is a claim, never trusted — and `headPoster` is one object-store `HEAD`, so republishing an unchanged concert costs nothing. |

### Authentication, and the wall between surfaces

zäme has three unrelated credentials and they must never substitute for one
another:

| Surface | Credential |
|---|---|
| `/api/invites/**` | the invite capability URL — the link IS the credential |
| `/api/host/**`, `/api/me/**` | the magic-link better-auth session cookie |
| `/api/v1/**` | `ZAEME_SERVICE_TOKEN`, one caller (Enterprise), no cookies |

The service token authenticates the *system*; the `x-mcp-user` header says which
Enterprise owner the call acts for, and it must equal `ZAEME_ENTERPRISE_OWNER_ID`
— an unrecognised id is a `403`, never a silent fallback to "the owner". Tokens
are compared in constant time (both sides hashed to a fixed width first, so a
length mismatch cannot throw and become its own oracle), and a missing token, a
wrong token and an unconfigured instance all take one code path and answer one
`401`.

Enterprise also stamps four provenance headers — `x-mcp-user`, `x-mcp-thread`,
`x-mcp-model`, `x-mcp-basis`. zäme accepts and carries them. It records nothing
from them yet; the point is that the option to start recording "which
conversation caused this write" stays open.

### How it is kept honest

- `test/api-contract.test.ts` asserts a **bijection**: every operation in the
  spec has a route, and every `/api/v1` route appears in the spec. A route the
  spec omits is as much a bug as an operation with no route — Enterprise would
  generate a tool for the latter and get a 404 at runtime. It also pins the 33
  tool names and asserts the spec's quoted `yes`/`no` literals survive parsing as
  strings (unquoted, YAML 1.1 turns them into booleans).
- `test/api-boundary.test.ts` asserts the credential separation structurally
  over the source, and unit-tests the constant-time comparison.
- `scripts/api-smoke.sh` (`pnpm smoke:api`) exercises the whole surface against a
  running server with a real database — including both directions of the
  boundary with a genuine magic-link session and a genuine service token.

## Self-hosting Considerations

- **Single binary mentality**: `docker compose up` should be the entire deployment story.
- **Migrations on startup**: Drizzle migrations run automatically. No manual migration step.
- **Graceful feature degradation**: `ENABLE_AI`, `ENABLE_SBB`, `ENABLE_MAGIC_LINK` flags allow deploying without optional external dependencies.
- **No telemetry**: zäme phones home to nobody. No analytics, no error reporting to third parties unless you add it yourself.
- **Backup**: The only stateful components are the PostgreSQL database and R2 storage. Both are the self-hoster’s responsibility.

-----

## Security Notes

- RSVP tokens and iCal feed tokens are unguessable cuid2 strings. Treat them as credentials.
- Presigned R2 URLs expire after 15 minutes.
- All API routes validate session or token before responding.
- The `/mcp` endpoint requires admin authentication.
- Guest access is scoped strictly to the event they were invited to.
