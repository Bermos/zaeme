# Architecture

This document describes the technical architecture of zäme. It is intended as a living reference for contributors and self-hosters who want to understand how the pieces fit together.

It describes what is **built**. Where something is planned but not written, it says so, or it is not here at all — [ROADMAP.md](./ROADMAP.md) is the place for intentions.

-----

## Overview

zäme is a single-tenant, full-stack Nuxt 4 application — one flat package, no pnpm
workspace, no `packages/*`, no Nuxt layers. “Single-tenant” means one instance
serves one person (the owner) and their friends. There is no concept of
organisations, workspaces, or cross-user isolation beyond the event permission
model.

```
Browser                                   Enterprise (the only machine caller)
  │                                          │
  ├── SSR pages (invite pages / OG previews) │
  ├── SPA navigation (after initial load)    │
  │                                          │
  └── Nuxt Server ◄──────────────────────────┘
        ├── /api/public/**   published events, no credential
        ├── /api/invites/**  the invite capability URL IS the credential
        ├── /api/host/**     the planner's own events (session)
        ├── /api/me/**       cross-event view for a signed-in account
        ├── /api/admin/**    session + instance owner
        ├── /api/v1/**       the machine API (service token, no cookies)
        ├── /calendar/*.ics  iCal feed routes
        ├── /healthz         readiness (Kitchen reads this)
        │
        ├── Better Auth      magic link + passkey, one session
        ├── Drizzle ORM      database access (node-postgres)
        └── Inngest client   background job dispatch
```

There is **no `/mcp` endpoint and no LLM in the request path**. Enterprise
generates its MCP tool surface from zäme's OpenAPI contract instead; see
[Machine API](#machine-api--enterprises-reach-into-zäme-adr-0036).

## Data Layer

### Database

Plain PostgreSQL, reached over the wire protocol with
[node-postgres](https://node-postgres.com) and wrapped in Drizzle ORM for schema
definition, migrations and queries. One memoised pool and one Drizzle client,
both in `server/utils/db.ts`, bound to the whole schema so better-auth's adapter
and the domain's query builder share a connection pool.

`DATABASE_URL` is the entire configuration. (This repo once used Neon's
serverless HTTP driver; that driver cannot reach an ordinary Postgres on :5432,
which is what the deployment platform provisions, so it is gone.)

Schema lives in `server/database/schema/` — five files, not one per domain:

```
server/
  database/
    schema/
      auth.ts           zaeme_user, zaeme_session, zaeme_account,
                        zaeme_verification, zaeme_passkey
      events.ts         every events_* table (the whole social domain)
      audit.ts          zaeme_audit_log
      geocode.ts        zaeme_geocode_cache
      index.ts          re-exports all four
    drizzle.config.ts   drizzle-kit config
    migrations/         generated by drizzle-kit — never hand-written
  utils/
    db.ts               pool + db singleton
```

Migrations are generated with `pnpm db:generate` and applied with `pnpm db:migrate`
locally, or by `scripts/migrate.mjs` as a pre-release task in deployment. They are
forward-only and idempotent; nothing has a down step.

### IDs

All primary keys use [cuid2](https://github.com/paralleldrive/cuid2) — URL-safe, sortable, no UUID visual noise. Generated in application code before insert, never by the database.

### Guest identity is an email address

This is the single most load-bearing convention in the schema. A guest has **no
account**: they are identified by their lowercased email address, everywhere. An
RSVP is unique per `(event, email)`, a date vote per `(option, email)`, a series
membership per `(series, email)`, a bring-list claim carries the claimer's email.

A `zaeme_user` account is *optional* and adds exactly two things: the cross-event
“all my invites” view at `/me`, and the host surface. It does not change how a
guest's answers are stored.

### Tables at a glance

| Table | Holds |
|---|---|
| `events_event` | the gathering: type, status, dates, location, poster, visibility, series parent |
| `events_event_planner` | who can plan it — `owner` \| `co_planner` \| `logistics` |
| `events_planner_invite` | a capability link that makes another account a co-organizer |
| `events_invite` | the guest capability link; `tier` (`core` \| `general`) phases a party |
| `events_rsvp` | the answer — `yes` \| `maybe` \| `no` \| `cheering`, +1, dietary, accessibility, notes |
| `events_date_option` / `events_date_vote` | the date-finding poll; answers are `yes` \| `ifneedbe` \| `no` |
| `events_contribution` | the bring list — who brings what, claimed by email |
| `events_expense` / `events_expense_share` | the trip budget, in integer cents |
| `events_timeline_item` | the itinerary |
| `events_media` | photos, videos, documents and tickets |
| `events_series_member` | the standing group of a recurring series |
| `events_message` | the per-event group chat |
| `events_ical_token` | the per-person calendar-feed credential |
| `zaeme_*` | better-auth: users, sessions, accounts, verifications, passkeys |
| `zaeme_audit_log` | one row per mutating request on a credentialled surface |
| `zaeme_geocode_cache` | one row per place search already answered, so the geocoder is asked once |

Table names carry the `events_` prefix; the JS exports drop it, so domain code
reads `tables.event`, `tables.rsvp`. Enum-ish columns are `text({ enum })` rather
than real Postgres enums — same TypeScript union, far simpler migrations.

### Domain logic

Everything that is not an HTTP concern lives in `server/domain/` and is re-exported
from `server/domain/index.ts`. Route handlers validate with zod, call one domain
function, and project the result. The domain is deliberately dependency-light — it
does not import Inngest; proactive dispatch is injected by the caller as an
`EventDispatch` (`server/utils/dispatch.ts`), so the domain stays testable and the
background-job library stays replaceable.

`server/domain/admin.ts` is the exception to the user-scoped rule: its reads are
*instance*-scoped, for the owner's cross-event views. Read the warning at the top
of that file before adding one.

## Authentication

[Better Auth](https://better-auth.com) over the `zaeme_*` tables — zäme's own
multi-user instance, unrelated to any other better-auth setup.

### Two sign-in methods, one credential

| Method | Who | Notes |
|---|---|---|
| Magic link | Guests, and anyone who prefers it | Needs a working mail transport |
| Passkey | The owner, and anyone who adds one | WebAuthn; needs nothing but a browser |

They end in the **same session cookie on the same account**, so nothing
downstream (`requireGuestUser`, `requireOwner`, the audit recorder) learns a
second shape. There are no passwords and no email+password strategy. There are
no `ENABLE_*` flags: a magic link is offered when a mail transport exists and
withheld — visibly, with an explanation — when it does not.

The WebAuthn relying-party id and origin are derived from the one URL the
instance already knows it is served at (`BETTER_AUTH_URL`, then `BASE_URL`, then
`KITCHEN_URL`), rather than configured a second time and left to drift. A
credential registered against the wrong `rpID` silently never matches.

### Passkey bootstrap — the two circular cases

Registering a passkey normally requires a session. Two moments make that
circular, and `server/utils/passkey-bootstrap.ts` is the whole of the decision:

1. **First run.** A fresh instance has no account, so there is nobody to be a
   session of. `/setup` claims the instance with a passkey.
2. **A locked-out owner.** An instance deployed without a mail transport can send
   a magic link nowhere, and its owner cannot sign in to register the passkey
   that would fix it. The break-glass is `ZAEME_OWNER_BOOTSTRAP_TOKEN`: a secret
   the operator puts in the environment, quotes once at `/setup/recover`, and
   then removes.

Both arrive as an opaque `context` string from the browser, and **both are decided
server-side** — against whether any account exists, and against a secret only the
environment holds. The browser asserts nothing that is believed. The token
resolves the owner and nobody else; it is not a session, it grants exactly one
passkey, comparison is constant-time over fixed-width hashes, every use is
audited, and the token never appears in a row, a log line or a response. With the
variable unset there is no second door at all.

The file is imported by `server/utils/auth.ts` and by **no route handler**;
`test/api-boundary.test.ts` asserts that. Changing it means running
`pnpm smoke:passkey`, which drives the real ceremony with a software
authenticator — nothing else proves it.

### The three credentials

They are never interchangeable, and `test/api-boundary.test.ts` enforces the
separation structurally, in both directions:

| Surface | Credential |
|---|---|
| `/api/public/**` | none — published events only |
| `/api/invites/**` | the invite capability URL — the link IS the credential |
| `/api/host/**`, `/api/me/**` | the better-auth session cookie |
| `/api/admin/**` | that same session, AND being the instance owner |
| `/api/v1/**` | `ZAEME_SERVICE_TOKEN`, one caller, no cookies |

No `/api/v1` handler may read a cookie, and no guest or host handler may read the
service token.

### Roles

| Role | Description |
|---|---|
| Instance owner | The FIRST account registered (`server/utils/instance.ts`). The only one that reaches `/admin`. |
| Account | Any other account. Can host events and be a co-planner on others'. |
| Guest | No account. Identified by their lowercased email + an invite link. RSVPs, votes, claims, chats, uploads. |

Ownership is not a column and not an env var: it is “the first row in
`zaeme_user` by `created_at`”. There is nothing to set, nothing to keep in sync,
and no second place it could disagree with itself. (There is no `ADMIN_EMAIL`.)

Within one event the planner roles are separate: `owner`, `co_planner`,
`logistics` on `events_event_planner`. Planning an event and administering the
instance are different powers — a co-planner has the first and never the second.

### First-run

On first server start with an empty database nobody has claimed the instance, so
`server/middleware/setup.ts` redirects every surface that needs an account to
`/setup`, where the first account is created. The guest capability URLs, the
public pages, the calendar feeds and `/api/v1` are exempt — a guest holding an
invite link must never be bounced into an admin flow, and no HTTP client can act
on a redirect to a browser bootstrap page. `/api/admin` is deliberately NOT
exempt: an unclaimed instance has no owner, so it has no admin.

`GET /api/setup/status` is the open, account-free answer to “how do I get in
here”: whether setup is required, whether mail works, which transport, and
whether a break-glass token is installed. It never says what the token is.

## Event Lifecycle

```
draft ──→ polling ──→ published ──→ completed
  │                                    │
  └──────────────────────────────→ cancelled
```

| Status      | Description                                    |
|-------------|------------------------------------------------|
| `draft`     | Visible to planners only. Brainstorm mode.     |
| `polling`   | Date poll is open. Invite link not yet active. |
| `published` | Invite link active. RSVPs open.                |
| `completed` | Event is past. Read-only, media/memories mode. |
| `cancelled` | Soft-cancelled. Attendees notified via email.  |

Status transitions are explicit server actions, not automatic. Locking the poll
(`POST …/lock`) sets `startsAt`/`endsAt` from the winning option and moves
`polling → published`.

## Event Types

| Type      | Differences                                                                           |
|-----------|---------------------------------------------------------------------------------------|
| `hosted`  | Full feature set. You are organising.                                                 |
| `concert` | `ticketUrl` and `performerNote` shown, RSVP mode is `cheering`. Publicly visible by default. |
| `series`  | Parent container. Has child occurrences (`parentId`) and a standing member list that each new occurrence auto-invites. |
| `trip`    | Multi-day. Itinerary and shared budget are the point.                                 |
| `party`   | Two-stage: a small `core` invite wave fixes the date in the poll, then `general` invites go out once it is locked. |

`externalRef` marks an event that is a **projection** of a record owned
elsewhere — today only a concert published through `POST /api/v1/concerts/publish`.
It is the idempotency key for that operation, unique where present, null for
everything planned inside zäme.

| Timeline | `events-data.ts` | read via the invite page | `…/timeline` (POST/PATCH/DELETE) | `EventTimeline.vue`, `HostTimelineCard.vue` |
| Media | `media.ts` | `…/media/presign`, `…/media/confirm` | same + assign a ticket, delete | `MediaGallery.vue`, `HostMediaCard.vue` |

| Public listing | `public.ts` | `/api/public/events` | — | `/concerts`, `/e/{slug}` |

Chat is **request/response**, not streaming: `GET`/`POST` on the messages routes,
no SSE endpoint and no WebSocket. Messages have an author name, an email and an
optional `authorUserId` (set when a planner posted from the host side, so the UI
can badge them). There is no threading, no soft delete and no announcement mode.

### Timeline / Itinerary

Ordered `events_timeline_item` rows per event.

| Column      | Description                                                              |
|-------------|--------------------------------------------------------------------------|
| `type`      | `transport` \| `activity` \| `accommodation` \| `meal` \| `other`       |
| `sortOrder` | Integer; items are displayed ascending by `sortOrder`, then `startsAt`.  |
| `icon`      | Optional Lucide slug override — falls back to the type default.          |
| `pollId`    | Reserved forward-reference to a date-poll option, for items that depend on which slot wins. The column exists; nothing reads it yet. |

**Media pinning**: any `events_media` row can be attached to a timeline item via
`timelineItemId`. Pinned media appears in-line under its itinerary step.

The host surface has full CRUD including `PATCH`, so an item can be edited in
place and moved with up/down controls (`HostTimelineCard.vue` swaps `sortOrder`
with the neighbour — there is no drag-and-drop). The machine API has no `PATCH`:
it can add and remove timeline items but not edit one, and the operationId
`updateTimelineItem` is reserved in the spec for whoever closes that gap.

## File Storage

Any S3-compatible object store, through one seam (`server/utils/storage.ts`) —
Cloudflare R2, MinIO and Garage all work, and no handler contains storage
specifics. Config comes from `S3_*` environment variables, with the older `R2_*`
names accepted as aliases; for R2 the endpoint is derived from the account id
when not given. **Storage is optional** — `isStorageConfigured()` is false without
it and the upload surfaces say so.

Guest and host uploads go straight from the browser to the store:

```
Browser → POST …/media/presign  → zäme signs a PUT (15 min, content type and
                                   length bound into the signature)
        → PUT {presignedUrl}     → direct to the object store
        → POST …/media/confirm   → zäme records the media row
```

Key structure:

```
{eventId}/{mediaType}/{mediaId}.{ext}
```

The one exception is poster art arriving on the machine API
(`PUT /api/v1/media/posters/{sha256}`): those bytes land on zäme's own request, so
zäme writes the object itself and verifies the SHA-256 server-side — the path is a
claim, never trusted. Poster art is then served from a stable, non-expiring route
(`/api/public/poster/{key}`) whose authorisation is re-derived from the domain:
the bytes resolve only while some public, published event still points at that
key. Take the concert down and the poster stops resolving.

## Background Jobs

[Inngest](https://inngest.com). Functions are defined in `server/inngest/functions/`
and served at `/api/inngest`. Without `INNGEST_EVENT_KEY` the client runs in dev
mode; delivery is fire-and-forget (`server/utils/dispatch.ts`) and a failure to
dispatch is logged, never allowed to fail the user's request.

Four functions exist:

| Job                | Trigger                             | Does                                           |
|--------------------|-------------------------------------|------------------------------------------------|
| `events/rsvp.confirmed`  | Attendee RSVPs yes/maybe      | Send confirmation email with `.ics` attachment |
| `events/event.published` | Event status → published      | Send invite emails                             |
| `events/event.reminder`  | Scheduled 48h before the event by `event.published` | Send reminder emails                           |
| `events/event.cancelled` | Event status → cancelled      | Notify everyone who answered                   |

The `events/` prefix is kept from the monorepo era so no persisted scheduled run
is orphaned.

## iCal / Calendar

Two routes, both unauthenticated in the HTTP sense and both secured by an
unguessable token — treat the tokens as credentials:

| Endpoint | Content |
|---|---|
| `GET /calendar/{token}.ics` | Every event the token owner has RSVP'd yes/maybe to |
| `GET /i/{token}/calendar.ics` | The single event behind that invite link (409 while the date is still being polled) |

Generated by `server/utils/ics.ts` using the [ics](https://www.npmjs.com/package/ics)
library, and attached to RSVP confirmation emails.

## Email

Three transports, tried in this order by `server/emails/send.ts`, and the order is
the design:

1. **The mail relay** — an HTTP endpoint in front of Proton Bridge, running as its
   own workload on the platform and bound in as `KITCHEN_SERVICE_MAIL` (or
   `MAIL_RELAY_URL`) plus `MAIL_RELAY_TOKEN`. First, because an instance that has
   one has deliberately built it.
2. **Resend**, for an instance with `RESEND_API_KEY`.
3. **A dry run** — the payload and every link in it on stdout. Not a failure: the
   request path keeps working, and the printed magic link is how an instance with
   no mail is bootstrapped at all.

**Never ask `RESEND_API_KEY` whether this instance can send mail** — ask
`server/utils/mail-status.ts`. `/login` and `/admin/security` use it to stop
offering a magic link an instance can deliver nowhere, which is the worst version
of the bug: a form that accepts an address, says “check your inbox”, and is
indistinguishable from a link that went to spam.

Templates live in `server/emails/templates/` and are rendered with
[React Email](https://react.email) through `server/emails/render.ts`:

```
server/emails/templates/
  _layout.ts
  invite.ts
  rsvp-confirmation.ts
  event-reminder.ts
  event-cancelled.ts
  magic-link.ts
```

## Machine API — Enterprise's reach into zäme (ADR-0036)

zäme owns the social domain outright. The Enterprise life-OS keeps no `events_*`
schema and no domain logic; it reaches zäme **only** over a versioned HTTP
contract, and its XO agent's whole events tool surface is GENERATED from that
contract at build time.

**The contract is [`docs/zaeme-api.openapi.yaml`](docs/zaeme-api.openapi.yaml),
and this repository's copy is the source of truth.** zäme serves it verbatim at
`GET /api/openapi.yaml`. The copy committed in `Bermos/Enterprise` is an
explicitly-labelled vendored snapshot, kept so their build can generate offline;
it is downstream of this one.

### Shape

- 30 paths, 40 operations, all under `/api/v1`.
- 33 carry `x-mcp-expose` (the default) and become MCP tools under exactly the
  names the XO already uses — `listEvents`, `scheduleSeriesShowing`,
  `createPartyPlan`, … An `operationId` is a tool name, so renaming one changes
  the model's vocabulary. `test/api-contract.test.ts` freezes the set.
- 7 are plumbing and are deliberately NOT tools: `getEventsSnapshot`,
  `getEventsAttention`, `publishConcert`, `unpublishConcert`, `uploadPoster`,
  `headPoster`, `getHealth`.
- Route handlers are thin. Every operation validates with zod, calls ONE
  `server/domain/` function and projects the result through
  `server/utils/v1-shapes.ts`, so a new column never silently joins a generated
  tool's output.

### Three that carry weight

| Operation | Why it is special |
|---|---|
| `getEventsSnapshot` | Fetched on EVERY XO turn before any tool call. One SQL statement (a `mine` CTE with scalar sub-selects), strong `ETag` + `private, max-age=60, stale-while-revalidate=600` so the steady state is a 304, and it degrades to a valid snapshot with `degraded: true` rather than 5xx. |
| `getEventsAttention` | The facts half of the daily check-in. Stateless and side-effect free; Enterprise keeps the unread guard, the once-a-day throttle and the escalation. |
| `uploadPoster` / `headPoster` | Poster art is content-addressed by SHA-256. The digest is verified **server-side** — the path is a claim, never trusted — and `headPoster` is one object-store `HEAD`, so republishing an unchanged concert costs nothing. |

### Authentication, and the wall between surfaces

The machine API's credential is `ZAEME_SERVICE_TOKEN`, and it is one of the
[three credentials](#the-three-credentials) that never substitute for one another.

The admin surface adds no fourth credential — it is the host session plus one
question (`server/utils/admin.ts`) — but it is a fourth WALL: Enterprise's
service token must not reach it. The machine API is a peer of the admin surface,
not a way into it; a service token that reached `/api/admin` would hand the XO
the instance's accounts, every live invite link, and the audit of its own
behaviour.

The service token authenticates the *system*; the `x-mcp-user` header says which
Enterprise owner the call acts for, and it must equal `ZAEME_ENTERPRISE_OWNER_ID`
— an unrecognised id is a `403`, never a silent fallback to "the owner". Tokens
are compared in constant time (both sides hashed to a fixed width first, so a
length mismatch cannot throw and become its own oracle), and a missing token, a
wrong token and an unconfigured instance all take one code path and answer one
`401`.

Enterprise also stamps four provenance headers — `x-mcp-user`, `x-mcp-thread`,
`x-mcp-model`, `x-mcp-basis`. zäme accepts and carries them, and since the admin
surface landed it also RECORDS them: every machine-surface write writes a
`zaeme_audit_log` row carrying the thread, the model and the basis message ids.
That is the act, not the diff — linking a specific written row back to the
sentence that caused it is issue #12, and wants its own table.

### How it is kept honest

- `test/api-contract.test.ts` asserts a **bijection**: every operation in the
  spec has a route, and every `/api/v1` route appears in the spec. A route the
  spec omits is as much a bug as an operation with no route — Enterprise would
  generate a tool for the latter and get a 404 at runtime. It also pins the 33
  tool names and asserts the spec's quoted `yes`/`no` literals survive parsing as
  strings (unquoted, YAML 1.1 turns them into booleans).
- `test/api-boundary.test.ts` asserts the credential separation structurally
  over the source, and unit-tests the constant-time comparison.
- `scripts/api-smoke.sh` (`pnpm smoke:api`) exercises the whole surface against a
  running server with a real database — including both directions of the
  boundary with a genuine session and a genuine service token. Since #14 it runs
  in CI too, in the `api` job: service containers for Postgres and an
  S3-compatible store, then the BUILT server (`.output/server/index.mjs`, not
  `pnpm dev`) waited for on `/healthz`. The job fails if any check *skips*, so a
  missing credential degrades it loudly rather than quietly proving less.
- `scripts/passkey-smoke.mjs` (`pnpm smoke:passkey`) runs the real WebAuthn
  ceremony with a software authenticator, and runs **nowhere but a terminal** —
  a green pipeline says nothing about the passkey surface.

## The admin surface (owner-only)

`/admin` is where the instance is administered, and where the questions that
span events are answered. It exists because the split from the Enterprise
monorepo (ADR-0036) left zäme standing on its own: the owner's cross-event views
used to be an Events department in a shell that could query the whole table, and
the operator concerns — accounts, tokens, storage, an audit — had no home at all
while somebody else was the operator.

**Who.** The instance owner, and nobody else. `server/utils/admin.ts` resolves
the session (the same cookie the host surface uses) and then asks whether that
account is the first one registered. A co-planner gets `403`, not `404` — they
are real, they are simply not the owner. The gate is imported nowhere but
`server/api/admin/**`, and the boundary test asserts it.

**What.**

| Page | Answers |
|---|---|
| `/admin` | upcoming / total / drafts, plus the gatherings quietly failing to happen |
| `/admin/events` | every event with its counts, filtered; filters live in the URL |
| `/admin/calendar` | a month grid across every event |
| `/admin/series` | every series and its occurrences |
| `/admin/people` | everybody the instance knows, keyed by the email that IS guest identity |
| `/admin/invites` | every capability link, with revoke and restore |
| `/admin/media` | the media library and what it costs to store |
| `/admin/accounts` | who can sign in; sign-out-everywhere; deletion that keeps their answers |
| `/admin/security` | passkeys on the owner account, whether mail works, and whether a break-glass token is still installed |
| `/admin/integration` | the Enterprise link: credential fingerprint, mapping, whether it is calling |
| `/admin/audit` | who did what, including what was refused |

**Reads live in `server/domain/admin.ts`** and are instance-scoped rather than
planner-scoped — the rest of the domain is user-scoped and stays that way. These
are the views with real volume, so counts are scalar sub-selects or grouped
aggregates inside the same statement; there is no query-per-row anywhere. Note
the warning at the top of that file about drizzle rendering an interpolated
column unqualified inside a `sql` template: it produced a sub-select that
silently counted zero, and it had already shipped once.

### The audit log

`zaeme_audit_log` records one row per mutating request on a credentialled
surface: who, which surface, which event, and the response status — so a REFUSED
attempt is as visible as a successful write, which is most of what an audit is
for. Reads are not recorded; Enterprise fetches the snapshot on every XO turn
and a log of that would bury everything else.

Two writers, and the split between them is the boundary again:

- `server/middleware/audit.ts` records the human surfaces at the edge, which is
  what makes the log complete — a handler-by-handler convention is one forgotten
  call away from a hole. It returns immediately for `/api/v1` and `/api/auth`:
  no cookie may be read near the machine surface, and magic-link tokens travel
  in those auth URLs.
- `defineServiceHandler` records the machine surface from its own credential,
  with the provenance headers attached.

A new route needs no audit code of its own.

Writing never throws — a row is a record of something that already happened, and
failing the request because the record failed would trade a completed action for
a lost one. Retention is a button on `/admin/audit`, not a policy: on a personal
instance the log is small, and something that quietly deletes evidence is worse
than something that says what it removed.

## Build & Deployment

There is no Dockerfile and no compose file, deliberately. The upstream instance is
built by [Kitchen](https://github.com/Bermos/Kitchen) with buildpacks, configured
by `kitchen.json`:

- **Build**: buildpacks, framework detected as Nuxt.
- **Node version**: read out of `engines.node` in `package.json` into
  `BP_NODE_VERSION` and handed to the node-engine buildpack verbatim. That field
  looks like tidy-uppable boilerplate and is not — without it the app silently
  gets whatever Node is newest that day.
- **Migrations**: `scripts/migrate.mjs` runs as a `migrate` **task** before the
  release takes traffic. A failed task stops the deploy with the previous version
  still serving; the symptom is “my change is not there”, not an error page.
- **Health**: `GET /healthz` runs `select 1` — a replica that booted with an
  unreachable database is not ready, and a TCP connect could not tell that apart.
- **Port**: from `$PORT`. Nothing hard-codes 3000.

The OpenAPI contract travels inside the build as a Nitro server asset
(`nitro.serverAssets`), because `docs/` does not exist in `.output`.

Merging to `main` deploys. There is no release to hold.

## Self-hosting Considerations

- **Configuration is the feature flag.** There are no `ENABLE_*` variables. No
  storage config means no uploads; no mail transport means the magic link is not
  offered and says why; no service token means `/api/v1` authenticates nobody.
- **Migrations before traffic**, as a task, not an entrypoint step — an
  entrypoint migration runs once per replica, simultaneously, on every rollout.
- **No telemetry**: zäme phones home to nobody. No analytics, no error reporting
  to third parties unless you add it yourself.
- **Backup**: the only stateful components are PostgreSQL and the object store.
  Both are the self-hoster's responsibility.

## Security Notes

- Invite tokens and iCal feed tokens are unguessable cuid2 strings. They ARE the
  credential — treat them accordingly.
- Presigned upload URLs expire after 15 minutes and bind the content type and
  length; download signatures last an hour.
- Every route validates a credential before responding, and which credential is
  decided by where the route lives — enforced by `test/api-boundary.test.ts`, in
  both directions.
- Guest access is scoped strictly to the event they were invited to.
- The break-glass passkey token is absent unless deliberately installed, resolves
  the owner and nobody else, and every use is audited.
- Every mutating request on a credentialled surface leaves an audit row,
  including the ones that were refused.

## What is deliberately not here

So that nobody plans around something that does not exist:

- **No travel groups, no SBB integration.** There is no `originStation`, no
  clustering job and no transport.opendata.ch client. Planned — see ROADMAP phase 5.
- **No to-do lists and no pack lists.** Planned — ROADMAP phase 9. The bring list
  (`events_contribution`) is a different, shipped feature.
- **No LLM in the request path.** No Anthropic SDK, no `/api/ai/**`.
- **No `/mcp` endpoint.** Enterprise generates its tools from the OpenAPI contract
  instead; that is the shape phase 11 actually took.
- **No real-time transport.** Chat polls; there is no SSE endpoint and no
  WebSocket.
- **No i18n, no PWA manifest, no generated OG images.** Invite and event pages do
  set Open Graph meta, using the event's own poster as the image.
